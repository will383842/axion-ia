## Top 3 forces

1. **Sitemap-index manuel cohérent + lastmod différencié par catégorie** — `src/app/sitemap-index.xml/route.ts:88-143` lit `MAX(updatedAt)` réel par source (news / blog / knowledge) via 3 queries Prisma fail-soft, puis tombe sur `BUILD_TIME` ISO pour les sub-sitemaps non-DB (pages, faq, help, cas-concrets, villes-_, services-villes-_, comparaisons). Le commentaire P0-2 (`:65-77`) documente honnêtement la régression précédente (`new Date()` figé au module-load → tous lastmod identiques → Google désactive le signal). Cache `s-maxage=600` (10 min) après réduction P1-13 du 24h initial → nouvelles URLs visibles sous 10 min côté Cloudflare. `generateSitemaps()` (`sitemap.ts:254-302`) est partagé entre `/sitemap-index.xml` et la convention metadata Next 16 → zéro drift entre index et sub-sitemaps.

2. **Sitemap-news.xml conforme Google News + Top Stories** — `src/app/sitemap-news.xml/route.ts:133-189` émet namespace `xmlns:news`, `<news:publication>` + `<news:language>fr` + `<news:publication_date>` ISO 8601 + `<news:title>` XML-escapé, fenêtre stricte 48h via `NEWS_FRESHNESS_WINDOW_MS` (`:43`), cap 1 000 URLs (Google News spec), fail-soft P2021 si table absente. Sprint S+4-D 2026-05-18 a ajouté la fusion `Article isNews=true` ∪ `PRESS_RELEASES` (`:115-131` + `:155-157`) avec tri stable desc par `publication_date` → Google News + Discover voient les communiqués éditoriaux dans la fenêtre 48h.

3. **Build stub.invalid correctement propagé partout** — `src/server/exporters/knowledge-sitemap.ts:55-57` early-exit si `DATABASE_URL?.includes("stub.invalid")` → `buildKnowledgeSitemapChunk()` retourne `[]` au build GH Actions sans planter. Le `countKnowledgePublicEntries()` côté `sitemap.ts:292-295` retourne 0 chunks pendant le build → `knowledgeIds = []` → 0 sub-sitemap `knowledge-N.xml` injecté dans l'index au build. L'ISR `revalidate=3600` (`sitemap-index.xml/route.ts:57`) repopule sous 1h en prod quand le vrai `DATABASE_URL` est injecté par Coolify au runtime. Pattern propre, aligné sur le contrat ADR 0026.

## Top 3 gaps P1/P2

1. **P1 — Image-bank-villes-t{1,2,3-t4} sitemaps référencés sans guard `stub.invalid`** (effort 30 min). `src/app/sitemap-images-villes-t1.xml/route.ts` (et t2 / t3-t4 sœurs) sont listés dans `CUSTOM_SITEMAPS` de `sitemap-index.xml/route.ts:46-53` mais ces handlers — typiquement DB-aware (`image_assets` table) — n'ont pas le pattern early-exit `stub.invalid` qu'a `knowledge-sitemap.ts:55-57`. Au build GH Actions, si la route est crawlée pour pré-render (Next 16 `force-static`), un appel Prisma cassera silencieusement via le Proxy stub mais retournera un XML vide structurellement valide. Risque : sub-sitemaps **vides référencés dans l'index pendant les 60 min avant ISR run** → Google reçoit une promesse cassée. Mitigation : ajouter le même early-exit `stub.invalid` dans les 5 handlers `sitemap-images-*` + `sitemaps/images-{fr,en}` (cf. `images-fr.xml/route.ts:50` qui est `force-dynamic` donc OK mais cas dégradé identique).

2. **P2 — `knowledge-N.xml` mis sur `BUILD_TIME` lastmod alors qu'il devrait suivre `knowledge`** (effort 15 min). `sitemap-index.xml/route.ts:134-143` mappe les IDs : `if (id.startsWith("knowledge-")) return lastmods.knowledge;` — OK. Mais le `lastmods.knowledge` n'est calculé qu'à l'ISR cycle (`revalidate=3600`) côté `/sitemap-index.xml`, alors que le sub-sitemap `/sitemap/knowledge-N.xml` (rendu par `app/sitemap.ts` Next convention) n'a pas son propre lastmod par chunk. Google peut détecter incohérence entre `<lastmod>` index et l'absence de `<lastmod>` cohérent par URL dans le sub-sitemap (`buildKnowledgeSitemapChunk()` met le `updatedAt` réel par URL — OK en fait). Pas de bug fonctionnel mais ajouter un test unitaire qui vérifie que la max(updatedAt) des URLs d'un chunk ≤ lastmod déclaré dans l'index serait propre.

3. **P2 — Pas de monitoring fail-streak côté `pingIndexNow()` helper** (effort 1h). `src/lib/indexnow.ts:68-89` est fire-and-forget : le `void fetch(...)` log en `console.error` mais ne touche PAS au compteur Redis `indexnow:fail-streak` qu'utilise `content-indexnow-worker.ts:32-51` pour escalader vers Telegram à 3/10/30 fails. Conséquence : les pings IndexNow émis par les server actions (`features/admin-blog/actions.ts`, `features/admin-case-studies/actions.ts`, `features/admin-help/actions.ts`, `server/actions/content-gen/article.ts`) qui appellent directement `pingIndexNow()` (bypass du worker BullMQ — cf. commentaire `:5-10` qui le revendique pour éviter round-trip HTTP) **n'alertent jamais** Will si Bing tombe en panne. Recommandation : factoriser le `recordIndexNowFail` / `resetIndexNowFailStreak` du worker dans un helper partagé `src/lib/indexnow-fail-streak.ts` et l'appeler aussi depuis le helper `pingIndexNow()`.
