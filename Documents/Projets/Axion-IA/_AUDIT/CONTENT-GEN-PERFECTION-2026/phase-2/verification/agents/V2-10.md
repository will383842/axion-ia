### Documentation best-effort ✅
```typescript
// P0-10 — best-effort post-transaction : l'article est déjà en DB et publié.
// Un échec de l'enqueue d'indexation NE doit PAS rollback ni masquer la publication.
try {
  await enqueueIndexingForTier1(article.id, ...);
} catch (err) {
  console.warn('[content-publish-worker] indexing enqueue failed (best-effort):', err);
  await logStepError(cgJob.id, 'indexing_enqueue', err);
  // Pas de rethrow — article reste PUBLISHED
}

// P0-10 — best-effort post-transaction : un échec revalidate NE doit PAS masquer la publication.
// L'article reste publié et sera servi via ISR 1h naturellement.
try {
  await revalidateContent(article.slug, locale);
} catch (err) {
  console.warn('[content-publish-worker] revalidate failed (best-effort):', err);
  // Pas de rethrow
}
```

### Mécanisme de re-tentative ✅
- `enqueue.ts` : jobId déterministe `indexnow-${articleId}-${event}` → idempotence BullMQ native
- `content-indexnow-worker.ts` : fail streak Redis avec alertes Telegram aux seuils 3/10/30 fails consécutifs
- `content-tier-lifecycle-worker.ts` : appelle `enqueueIndexingForTier1` lors des promotes CTR-based → chemin de re-ping indirect

### Gap mineur V1 acceptable
Pas de flag DB `needsIndexingRetry` ni cron backfill "articles sans ping" — acceptable en V1 selon doctrine. ISR 1h couvre le revalidate.
