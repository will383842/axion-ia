## Migration SQL vérifiée

`prisma/migrations/20260521150300_add_performance_indexes/migration.sql` (commit 17c53bc) :

```sql
-- Index 1
CREATE INDEX CONCURRENTLY IF NOT EXISTS "articles_status_published_at_idx"
  ON "articles"("status", "published_at" DESC);

-- Index 2
CREATE INDEX CONCURRENTLY IF NOT EXISTS "gen_prov_article_timestamp_idx"
  ON "generation_provenance"("article_id", "timestamp" DESC);

-- Index 3
CREATE INDEX CONCURRENTLY IF NOT EXISTS "keywords_vertical_priority_idx"
  ON "keywords"("vertical", "last_used_at" ASC NULLS FIRST, "usage_count" ASC);
```

Les 3 index utilisent `CONCURRENTLY` (bonne pratique prod, pas de lock table) et `IF NOT EXISTS` (idempotence). Alignés exactement avec les specs P0-8.

## Points d'attention

### Divergence schema.prisma / migrations SQL (intentionnelle)
Les `@@index` composites correspondants ne sont PAS dans schema.prisma (seuls des index simples séparés existent). C'est intentionnel : Prisma DDL ne supporte pas `CONCURRENTLY`, donc la migration manuelle est la bonne approche pour une table prod avec données.

**Risque** : `prisma migrate diff` signalera une divergence. Acceptable et à documenter.

### locked_until/locked_by (colonne Keyword)
La migration 150100 ajoute `locked_until` et `locked_by` à la table keywords, mais ces colonnes ne sont pas couvertes par l'index keywords_vertical_priority_idx. La requête `WHERE locked_until IS NULL OR locked_until < now()` est un filtre post-lookup d'index. Acceptable pour 747 seeds, à monitorer au-delà de 10K keywords.

### psql inaccessible
EXPLAIN ANALYZE non exécutable depuis cet environnement. Déduction par preuve SQL : les index sont présents si `prisma migrate deploy` a tourné. Test manuel recommandé en prod.
