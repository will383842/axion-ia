### Gestion 429 Anthropic

Trouvée et solide dans `axionia/src/server/content-gen/providers/anthropic.ts` :

```typescript
// anthropic.ts:93-95
if (status === 429) {
  return new ProviderError(`Anthropic rate limited`, "rate_limited", "anthropic", true);
}
```

La ProviderError avec `retryable: true` déclenche le retry exponentiel dans `withRetry()` :
- 3 tentatives max
- Délais : 10 000ms / 30 000ms / 60 000ms
- Auth failed / cost_cap_reached : `retryable: false` → pas de retry

**Problème identifié (P1)** : Le retry ne respecte pas le `Retry-After` header qu'Anthropic retourne sur 429. Le délai de 10s fixe peut être insuffisant si Anthropic impose un cooldown plus long. Le SDK `@anthropic-ai/sdk` expose `err.headers['retry-after']` mais ce n'est pas lu.

**Calcul coût réel Sonnet 4.6 (pricing code exact)**
- input : $3.00/1M tokens
- output : $15.00/1M tokens
- cache_read : $0.30/1M tokens
- cache_write : $3.75/1M tokens

Blog standard (2500 input + 3000 output, pas de cache) :
`2500 × $3/1M + 3000 × $15/1M = $0.0075 + $0.045 = $0.0525`

Guide pilier (12k input + 9k output) :
`12000 × $3/1M + 9000 × $15/1M = $0.036 + $0.135 = $0.171`

## 2. Limites OpenAI Embeddings (14/20)

### Flag OPENAI_EMBEDDINGS_ENABLED — Coverage complète

**Fichier** : `axionia/src/server/content-gen/dedup/openai-embedder.ts:64`

```typescript
if (process.env["OPENAI_EMBEDDINGS_ENABLED"] !== "true") return null;
```

- Default : OFF (pas de coût imprevu si env var absente ou non "true")
- Flag contrôle uniquement les embeddings dedup (couche B.7, text-embedding-3-large 1536 dim)
- N'affecte PAS les embeddings KB Voyage AI (piloté séparément par `VOYAGE_API_KEY`)

**Points positifs** :
- Flag coupe réellement 100% des appels OpenAI embeddings
- Si flag ON mais `OPENAI_API_KEY` absente → throw configuration error (fail-fast)
- Cap journalier in-memory : `OPENAI_EMBEDDINGS_MAX_TOKENS_PER_DAY` (default 1M tokens = ~$0.13/jour)
- Estimation tokens préalable au call (4 chars/token)

**Fallback si désactivé** :
La fonction `embed()` retourne `null`. Le caller (`dedup-guard.ts`) reçoit null et continue sans la couche embedding cosine — le pipeline ne bloque pas. C'est un **fail-soft intentionnel**, documenté.

**Problème P2 — batch vs 1-par-1** :
L'embedder appelle l'API OpenAI 1 texte par fois (pas de batch) :
```typescript
body: JSON.stringify({ model: EMBEDDING_MODEL, input: text, ... })
```
OpenAI supporte jusqu'à 2048 inputs par requête. Sur 500 articles/jour, cela représente 500 appels HTTP au lieu de ~1. Impact coût minimal ($0.13/jour max de toute façon) mais impact latence réel sur high-volume.

**Problème P1 — counter in-memory non thread-safe entre processus** :
```typescript
const tokenCounter = new Map<string, number>();  // in-memory, reset au boot
```
Si N workers tournent en processus séparés (Coolify multi-instance), chaque processus a son propre compteur → le cap journalier effectif est `N × 1M tokens` au lieu de 1M. L'audit note : "V2 : Redis-backed" mais V1 a ce gap.

**topic-fingerprint.ts (Voyage AI)** : STUB complet — retourne toujours `null` même si `VOYAGE_API_KEY` est présente (TODO Sprint S+2). Zero coût donc, mais zero protection sémantique.

## 3. Cap journalier MAX_PUBLISH_PER_DAY (18/25)

### Implémentation exacte

**Fichier** : `axionia/src/server/queue/workers/content-publish-worker.ts`

```typescript
// Ligne 77 — définition
const MAX_PUBLISH_PER_DAY = parseInt(process.env.MAX_PUBLISH_PER_DAY ?? "30", 10);

// Ligne 137-138 — comptage depuis minuit UTC
const todayUtcStart = new Date();
todayUtcStart.setUTCHours(0, 0, 0, 0);
const publishedToday = await prisma.article.count({
  where: { publishedAt: { gte: todayUtcStart }, status: "published" },
});

// Ligne 141 — enforcement
if (publishedToday >= MAX_PUBLISH_PER_DAY) {
  await job.moveToDelayed(nextWindowTs, job.token);
  return;
}
```

**Points positifs** :
- Configurable via env var `MAX_PUBLISH_PER_DAY` (override Coolify possible)
- Default 30/jour (conforme Google Scaled Content Policy)
- Reset UTC (minuit UTC = comportement déterministe, timezone-safe)
- Drip window 8h–22h CET (signal publication humain, réduction HCU risk)
- Dépassement → `job.moveToDelayed()` vers prochain 8h CET (pas de drop, reschedulé)
- Log structuré JSON à chaque throttle : `event: "publish_throttled"`, `reason: "max_daily"`, `publishedToday`, `cap`

### Analyse thread-safety

**Problème P0 — race condition à haute concurrence** :

Le pattern `count → check → publish` n'est PAS atomique. Avec concurrency=3 sur `content-publish-worker` :

```
Worker A: count() → 29 (< 30) → procède
Worker B: count() → 29 (< 30) → procède en parallèle
→ 31 articles publiés ce jour (dépassement)
```

Il n'y a pas de lock Postgres, pas de `SELECT FOR UPDATE`, pas de compteur Redis atomique. Sur les volumes bas (30/jour), la fenêtre de race est courte, mais à 500/jour le problème devient systématique.

**Rampe progressive** : NON codée. Le cap est binaire (0 ou MAX). Aucune logique de rampe (ex : 10 articles les 7 premiers jours, 20 les 14 suivants, puis 30). Les commentaires n'en font pas mention non plus.

**Alerting si cap atteint** : Seulement via log JSON console. Pas d'alerte Telegram dédiée quand `max_daily` est atteint (contrairement au cost cap qui a `alertCostCap80`/`alertCostCap100` avec Telegram).

Présent sur les workers chokepoint (`sentry-worker.ts`) :

**Problème P1** : Sentry capture les erreurs worker en général, mais il n'y a **pas de capture Sentry dédiée sur les événements cost cap**. Le cost cap déclenche Telegram + ContentGenConfig audit trail, mais pas de Sentry event. Si Telegram est down, le seul signal est le log `console.warn`.

## P0 identifiés

### P0-1 — Race condition MAX_PUBLISH_PER_DAY (thread-safety)

**Fichier** : `content-publish-worker.ts` ligne 137-155  
**Impact** : À concurrency=3, le cap journalier peut être dépassé de 1-3 articles sur chaque check. Risque Google Scaled Content si target 500/jour.  
**Fix recommandé** : Compteur Redis atomique (`INCR content-gen:publish:daily:YYYY-MM-DD` + TTL 86400s) OU transaction Postgres `INSERT ... WHERE NOT EXISTS (SELECT 1 FROM articles WHERE publishedAt >= today AND COUNT >= cap)`.

## P1 identifiés

### P1-1 — Retry Anthropic 429 sans respect du Retry-After header

**Fichier** : `providers/anthropic.ts` + `lib/retry.ts`  
**Impact** : Délai fixe 10s peut être trop court si Anthropic impose 60s. Risque d'exhaustion des 3 retries inutilement.  
**Fix** : Lire `(err as Anthropic.RateLimitError).headers?.['retry-after']` et adapter `delayMs` en conséquence.

### P1-2 — Daily embedding counter non thread-safe (multi-process)

**Fichier** : `dedup/openai-embedder.ts` ligne 34-35  
**Impact** : Multi-instance Coolify → cap effectif multiplié par N instances. À 2 instances : 2M tokens/jour au lieu de 1M.  
**Fix** : Migrer vers Redis `INCRBY content-gen:embed-tokens:YYYY-MM-DD` avec TTL 86400s (noté "V2" dans le code).

### P1-3 — Pas d'alerte Telegram sur max_daily cap atteint

**Fichier** : `content-publish-worker.ts` ligne 148  
**Impact** : Throttling silencieux. Will ne sait pas que le pipeline est bloqué depuis 8h du matin jusqu'à 22h sans notification.  
**Fix** : Ajouter `alertPublishDailyCap(publishedToday, MAX_PUBLISH_PER_DAY)` dans `content-gen-alerts.ts`, fire-and-forget.

### P1-4 — Pas de Sentry event dédié sur cost_cap_reached

**Fichier** : `lib/cost-tracker.ts` — handleCostCapHit()  
**Impact** : Si Telegram est down au moment du cap, seul `console.warn` trace l'événement.  
**Fix** : Ajouter `captureException(new Error('cost_cap_reached'), { tags: { provider }, extra: { spent, cap } })` dans `handleCostCapHit`.

### P1-5 — Monthly cap Anthropic ($100) insuffisant pour 500 articles/jour

**Fichier** : `lib/config-reader.ts` ligne 19 (default) + DB  
**Impact** : Cap atteint en 2 jours à 500/jour → kill switch automatique → pipeline arrêté.  
**Fix** : Rehausser `monthlyCapUsd` Anthropic à $1500+ via admin avant d'activer `factoryAutoPublishAllBlogTypes=true`. Ajouter doc dans runbook `R02`.

### P1-6 — BUDGET_CAP_USD per-article hardcodé ($0.15)

**Fichiers** : `blog-article.ts:23`, `blog-from-keywords.ts:31`  
**Impact** : Non configurable via env ou DB. Un article guidé complexe sur sujet technique peut dépasser $0.15 (2 quality-loop + Anthropic fallback).  
**Fix** : Lire depuis `ContentGenConfig.quality_loop.budgetCapUsd` (déjà utilisé ailleurs dans la codebase) ou env `CONTENT_GEN_BUDGET_CAP_USD`.

### P1-7 — topic-fingerprint.ts STUB permanent

**Fichier** : `dedup/topic-fingerprint.ts:74-79`  
**Impact** : Même avec `VOYAGE_API_KEY` présente, la fonction retourne `null` (TODO Sprint S+2). La couche sémantique de dedup n'est jamais active. Risque HCU sur articles thématiquement similaires.  
**Fix** : Implémenter l'appel Voyage AI `embed-3-large` + projection SimHash 64-bit comme décrit dans le TODO.
