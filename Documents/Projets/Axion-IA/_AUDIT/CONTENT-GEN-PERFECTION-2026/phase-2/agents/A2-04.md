## 1. Logs structurés JSON (16/25)

### Architecture de logging

Le projet utilise **deux systèmes de log** coexistants :

| Système | Fichier | Nature |
|---|---|---|
| `logGeneration()` / `logStep()` | `src/server/content-gen/shared/generation-log.ts:85` | Structured — insert Prisma `GenerationLog` table |
| `console.log/warn/error` bruts | Tous workers | Non-structuré — stdout perdu en prod |

`logStep()` (ligne 112-125 de `generation-log.ts`) est un wrapper `logGeneration()` qui insert dans la table `GenerationLog` avec les champs : `jobId`, `level`, `step`, `message`, `metadata` (JSON). PII redaction via `redactGenerationMetadata()` (ligne 89-90). Format JSON correct en DB.

Mais `console.log/warn/error` restent très présents dans les workers content-gen (voir ci-dessous).

## 4. Traçabilité end-to-end (10/15)

### Schéma de traçabilité — IDs chainés

```
KeywordSeed (keywords.id)
    ↓  selectKeyword() → term
ContentGenJob.id  (UUID, créé par orchestrator)
    ↓  idempotencyKey = sha256(campaignId::slotIndex::contentType::anchor) [orchestrator l.248-255]
BullMQ Job.id = "gen-{contentGenJobId}"  [orchestrator l.295]
    ↓  processJob(job: Job<ContentGenJobPayload>)
GenerationLog.jobId = ContentGenJob.id  [logStep appelé à chaque étape]
    ↓  content-gen-worker persist outputJsonRaw
ReviewQueue.jobId = ContentGenJob.id  [content-gen-worker l.539]
    ↓  approved → content-publish-worker
BullMQ Job.id = "publish-{reviewQueue.id}"  [content-gen-worker l.577]
Article.generatedByJobId = ContentGenJob.id  [content-publish-worker l.252]
ArticleTranslation.articleId = Article.id
LLMProvenance.articleId = Article.id  [content-publish-worker l.322]
IndexNow ping → enqueueIndexingForTier1({articleId, slug})
```

**Corrélation disponible** :
- `ContentGenJob.id` est l'ID pivot : présent dans GenerationLog, ReviewQueue, Article.generatedByJobId, BullMQ jobId préfixé
- `CoverageCampaign.id` → `ContentGenJob.campaignId` → traçabilité campagne ✓
- `Article.outlineSimhash` persiste pour future comparaison cross-articles ✓

**Gaps traçabilité** :
- **Aucun `correlationId` / `traceId` / `requestId`** : grep confirm 0 occurrence dans `src/server/`. Les logs GenerationLog utilisent `jobId` (UUID Prisma) mais pas un trace ID qui traverse les limites BullMQ → Sentry → HTTP.
- **ID BullMQ ≠ ContentGenJob.id** : BullMQ Job.id = `"gen-{uuid}"` (préfixé), ce qui empêche la corrélation directe BullMQ board ↔ GenerationLog sans parsing.
- **Chain hash `chainHash` non présent** : pas de hash de la chaîne complète KeywordSeed→Article pour audit de provenance end-to-end.
- `tokensInput: 0` dans ContentGenJob (l.491) casse le lien coût analytique au niveau job (CostLedger séparé mais non joint dans GenerationLog).

## Recommandations

### Logger à adopter

Le socle `logStep()` + `GenerationLog` Prisma est **la bonne approche** — conserver et étendre. Ne pas migrer vers `pino`/`winston` en production : la table GenerationLog offre une requêtabilité SQL que les fichiers de log n'ont pas.

**Action immédiate** : créer un step `generation_cost` dédié (ou enrichir `llm_call`) avec :
```typescript
await logStep(contentGenJobId, "llm_call", "Generator output ready", {
  duration_ms: Date.now() - startedAt,
  tokens_input: output.tokensInput,    // ← manquant actuellement
  tokens_output: output.tokensOutput,  // ← manquant actuellement
  total_tokens: output.totalTokens,
  total_cost_usd: output.totalCostUsd,
  model_id: output.modelId,
  provider_key: output.providerKey,
});
```
Et corriger `content-gen-worker.ts:491` : `tokensInput: output.tokensInput ?? 0` (pas `0` hardcodé).

### Champs à ajouter

1. **`keyword_select`** : ajouter `campaign_id: contentGenJobId`, `duration_ms: Date.now() - kwStart`
2. **`dedup_check` pre-IA pass** : ajouter `max_levenshtein_score`, `corpus_checked_count`
3. **`orchestrator tick`** : logStep("validation") avec `enqueued_count`, `tick_budget`, `mode`
4. **Sentry breadcrumbs** : dans `captureWorkerError`, appeler `Sentry.addBreadcrumb` pour les steps GenerationLog récents (lookup 5 dernières entrées)

### BullMQ dashboard

Installer `@bull-board/api` + `@bull-board/nextjs` (Sprint 6 déjà planifié) ou exposer `/api/admin/queue-metrics` qui appelle `queue.getJobCounts()` (waiting/active/completed/failed) directement via BullMQ API — 1h de travail.

### correlationId

Ajouter `correlationId` = `contentGenJobId` dans les tags Sentry (`captureWorkerError`) comme tag additionnel pour permettre la recherche directe depuis le dashboard Sentry.
