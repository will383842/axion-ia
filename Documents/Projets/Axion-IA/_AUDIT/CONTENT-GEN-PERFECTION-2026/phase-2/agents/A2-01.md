### Problèmes identifiés (-6 pts)

**R-1 (−2 pts) — Divergence removeOnComplete/removeOnFail worker vs queue** : Les workers content-gen, content-publish, content-quality-improver, content-indexnow posent `removeOnComplete: { count: 1000 }` et `removeOnFail: { count: 5000 }` **directement dans le Worker** (ex: `content-gen-worker.ts:657-658`), mais la queue dans `queues.ts` pose aussi `removeOnComplete: { age: 7*24*3600, count: 1000 }` + `removeOnFail: { age: 30*24*3600, count: 5000 }`. Selon la doc BullMQ, les options `removeOnComplete`/`removeOnFail` du Worker prennent la priorité sur le `defaultJobOptions` de la Queue **seulement si posées au niveau Worker constructor** — ce qui est le cas ici. Les `age` de la Queue (7j/30j) sont donc silencieusement ignorés pour ces workers. Comportement incohérent non documenté.

**R-2 (−2 pts) — Aucune DLQ dédiée** : Les jobs qui épuisent leurs `attempts` tombent dans la ZSet `failed` Redis sans traitement automatique. Il n'y a ni queue `*-dlq-reprocess` ni cron de replay. Le seul mécanisme de récupération est manuel (BullBoard admin). Pour `content-publish` (blast radius élevé), un fail définitif nécessite une investigation manuelle sans filet.

**R-3 (−1 pt) — Tentatives inline sans backoff pour queues créées en worker** : Les instances `new Queue("content-gen", ...)` créées inline dans `content-orchestrator-worker.ts:68`, `content-rss-fetch-worker.ts:91`, etc., n'ont **pas de `defaultJobOptions`**. Les jobs enqueués depuis ces instances n'héritent donc d'aucun retry/backoff. Exemple : `content-orchestrator-worker.ts:287` enqueue vers `content-gen` sans `{ attempts, backoff }` dans les job options. Si la ligne `await getContentGenQueue().add(...)` fail (Redis transient), le job est perdu.

**R-4 (−1 pt) — content-orchestrator et content-rss-fetch : attempts=1** : Pour le worker orchestrateur (tick 15 min), `attempts: 1` signifie qu'un crash Redis transient pendant un tick résulte en 0 retry. Acceptable pour un cron (prochain tick dans 15 min), mais non documenté comme choix délibéré dans le code. Idem rss-fetch.

### Analyse pauseCampaign() exacte

**Fichier** : `src/server/actions/content-gen/coverage.ts:219-263`

```typescript
export async function pauseCampaign(id: string): Promise<void> {
  // 1. Update DB : CoverageCampaign.status = "paused"
  await prisma.coverageCampaign.update({ where: { id }, data: { status: "paused", pausedAt: new Date() } });

  // 2. Cherche les ContentGenJob avec status="queued" pour cette campagne (max 5000)
  const queuedJobs = await prisma.contentGenJob.findMany({
    where: { campaignId: id, status: "queued" },
    select: { id: true },
    take: 5000,
  });

  // 3. Pour chaque job, cherche le BullMQ job par ID préfixé "gen-{jobId}"
  //    Si état = waiting | delayed | waiting-children | prioritized → bullJob.remove()
  if (queuedJobs.length > 0) {
    const queue = getContentGenQueue();
    for (const job of queuedJobs) {
      const bullJob = await queue.getJob(`gen-${job.id}`);
      if (bullJob) {
        const state = await bullJob.getState();
        if (["waiting", "delayed", "waiting-children", "prioritized"].includes(state)) {
          await bullJob.remove();
        }
      }
    }
  }
  // 4. revalidatePath + logActivity
}
```

**Analyse critique** :

- **Purge correcte des waiting jobs** : La logique retire les jobs BullMQ en état `waiting`/`delayed` pour les jobs DB `queued`. C'est la bonne approche — pas de `queue.obliterate()` (qui purgerait toutes les campagnes), pas de `queue.pause()` (bloquerait le worker global).

- **Gap 1 — Jobs "running" non stoppés (comportement documenté mais gap)** : Les jobs déjà en cours d'exécution (`status: "running"` en DB, état `active` en BullMQ) ne sont pas interrompus. Le commentaire l'assume explicitement : *"Les jobs running sont laissés terminer (graceful — le worker vérifie campaign.status à chaque tick)"*. Mais `content-gen-worker.ts` **ne vérifie pas `campaign.status`** en cours de job. Il vérifie uniquement le `kill_switch` global. Donc un job `running` d'une campagne `paused` ira jusqu'au bout et persiste son contenu en DB. Ce n'est pas de la cross-contamination, mais c'est une pause non-gracieuse (article généré hors campagne active).

- **Gap 2 — Race condition entre orchestrator tick et pause** : L'orchestrateur tourne `*/15 * * * *`. Si un tick démarre 1 seconde avant `pauseCampaign()`, il peut enqueuer N jobs entre la mise à jour DB (`status=paused`) et la boucle de purge. Ces N jobs ne seront **jamais purgés** car ils n'existent pas encore lors du `prisma.contentGenJob.findMany({ status: "queued" })`. `coverage.ts:237-263`. Fenêtre de race = durée du tick orchestrateur (~seconds).

- **Gap 3 — Pas de `queue.pause()` sur la queue globale** : La pause est per-campagne (suppression des jobs BullMQ individuels), pas une pause Redis-side de la queue. L'orchestrateur re-créera des jobs à son prochain tick si `CoverageCampaign.status` n'est pas vérifié correctement. Vérification : `content-orchestrator-worker.ts:113` — `where: { status: "running" }` → la campagne `paused` est bien filtrée. La purge est donc suffisante si le tick futur respecte ce filtre.

- **Verdict** : `pauseCampaign()` est fonctionnelle pour l'usage normal (queue drainée proprement pour les waiting jobs). Les deux gaps sont des edge cases documentés (running jobs) ou des races fenêtre-courte.

### Problèmes concurrence (-4 pts)

**C-1 (−2 pts) — image-bank-enrich et image-bank-translate sans rate-limiter Claude** :
- `image-bank-enrich-worker.ts:32` : `concurrency: 2` sans `limiter`
- `image-bank-translate-worker.ts:31` : `concurrency: 2` sans `limiter`
Ces workers appellent Claude Sonnet 4.6 (via `ImageSeoEnrichmentService` et `ImageTranslationService`). En bulk import (73 images mentionné dans la mémoire), 2 appels parallèles sans rate-limit → risque de rate-limit Anthropic API (default 50 RPM Sonnet sur tier 1). Pas de `limiter: { max: X, duration: 60_000 }`.

**C-2 (−1 pt) — content-gen concurrency 5 hardcodé** : `content-gen-worker.ts:652` documente *"V1 concurrency 5 hardcoded — V2 DB-managed"* mais le champ `ContentGenConfig.workers_concurrency` mentionné en header du fichier n'est jamais lu. Si `workers_concurrency` est configuré à 2 en DB pour respecter un quota OpenAI, cette config est ignorée.

**C-3 (−1 pt) — Backpressure absente sur content-orchestrator** : L'orchestrateur enqueue jusqu'à `tickBudget` jobs sans vérifier la longueur de la queue `content-gen` (BullMQ `getWaitingCount()`). Si content-gen est saturée (ex: Redis backlog > 10k jobs), l'orchestrateur continue à empiler. Pas de `queue.getWaitingCount()` gate dans `content-orchestrator-worker.ts`.

## 4. Multi-campagnes parallèles (9/15)

### Test logique : 2 campagnes simultanées

**Scénario** : Campagne A (landing_ville Paris, 100 jobs) + Campagne B (blog_article, 50 jobs) toutes deux `status=running`.

#### Isolation au niveau orchestrateur

`content-orchestrator-worker.ts:113-158` :
```typescript
const runningCampaigns = await prisma.coverageCampaign.findMany({ where: { status: "running" }, orderBy: { createdAt: "asc" } });
const perCampaignTick = Math.max(1, Math.floor(tickBudget / runningCampaigns.length));
```

- Chaque campagne obtient `floor(20 / 2) = 10` jobs par tick. Distribution équitable.
- `campaignId` est posé sur chaque `ContentGenJob` créé : `content-orchestrator-worker.ts:265` — `campaignId: campaign.id`.
- `idempotencyKey` = hash(`campaignId + slotIndex + contentType + anchor`) : isolation parfaite au niveau DB.

#### Isolation au niveau content-gen-worker

`content-gen-worker.ts` ne filtre **pas** par campagne. Le worker pick le prochain job en queue FIFO/priority sans vérifier `campaignId`. **Les jobs des deux campagnes se mélangent dans la même queue** `content-gen` (concurrency 5). C'est architecturalement correct (une queue unique est le pattern BullMQ standard) mais implique :

1. **Pas de garantie d'équité entre campagnes** : si A enqueue 100 jobs avant B (timing tick), A monopolise la queue pendant ~20 jobs avant que B puisse démarrer.
2. **Pas de priority par campagne** : `priority: 5` hardcodé pour tous les jobs (`content-orchestrator-worker.ts:260`, `content-rss-fetch-worker.ts:249`). Impossible de prioriser une campagne urgente sur une autre.

#### Isolation au niveau publish/quality

Chaque `ContentGenJob` porte son `id` unique → `ReviewQueue.jobId` unique → pas de cross-contamination au niveau publish.

#### `campaignId` dans les jobs BullMQ

Le `campaignId` est dans la **DB row** (`ContentGenJob.campaignId`) mais **pas dans le payload BullMQ** (`ContentGenJobPayload`). Le worker récupère la DB row via `contentGenJobId` et a donc accès à `dbJob.campaignId` (utilisé à `content-gen-worker.ts:629` pour `alertBatchFail`). L'isolation est donc maintenue via la DB lookup, pas via le payload BullMQ.

### Gaps multi-campagnes (-6 pts)

**M-1 (−3 pts) — Pas d'isolation de queue par campagne ou priority différencié** :
Avec 2 campagnes simultanées, les jobs se mélangent dans une queue FIFO unique. Si une campagne génère une erreur systématique (ex: anchorVilleSlug invalide), elle consomme des retry slots qui impactent la throughput globale pour toutes les campagnes. Pas de `priority` variable ni de queue par campagne (ce dernier serait un over-engineering, mais le priority différencié serait simple).

**M-2 (−2 pts) — Kill switch global, pas per-campagne** : `content-gen-worker.ts:160-166` vérifie `ContentGenConfig.kill_switch.active` — un flag global. Pour pauser une campagne sans stopper l'autre, seule `pauseCampaign()` fonctionne (purge BullMQ + DB status). Mais les jobs déjà `active` dans BullMQ d'une campagne pausée continuent jusqu'au bout (gap documenté en section 3). Il n'existe pas de mécanisme `per-campaign kill` au niveau worker.

**M-3 (−1 pt) — `campaignId` absent du payload BullMQ** : `ContentGenJobPayload` (`content-gen-worker.ts:147-152`) ne contient pas `campaignId`. Pour obtenir la campagne d'un job depuis BullMQ Board admin (debugging), il faut faire un lookup DB sur `contentGenJobId`. Observabilité réduite.

## P0 identifiés (bloquants)

### P0-1 — Race condition pauseCampaign vs orchestrator tick

**Fichiers** : `coverage.ts:219-263` + `content-orchestrator-worker.ts:99-316`
**Risque** : Lors d'un `pauseCampaign()`, si l'orchestrateur est en train de ticker (15 min cron), les jobs nouvellement enqueués par ce tick ne sont pas purgés. Fenêtre ~1-5s. Impact : 10-20 jobs supplémentaires générés après pause.
**Fix recommandé** : Ajouter une vérification `campaign.status !== "running"` au début du tick orchestrateur après le `findMany` (déjà fait via le filtre), ET ajouter un second `findMany` post-purge pour les jobs créés pendant la boucle.

### P0-2 — image-bank-enrich/translate sans rate-limit Claude

**Fichiers** : `image-bank-enrich-worker.ts:18-38`, `image-bank-translate-worker.ts:17-38`
**Risque** : En bulk import (Will importe 73 images), 2 appels Claude Sonnet en parallèle sans limiter → rate-limit Anthropic → jobs failed → retry exponential → délai import.
**Fix recommandé** : Ajouter `limiter: { max: 20, duration: 60_000 }` aux deux workers.

## P1 identifiés (importants)

### P1-1 — Instances Queue inline sans defaultJobOptions

**Fichiers** : `content-gen-worker.ts:132-136`, `content-orchestrator-worker.ts:64-69`, `content-rss-fetch-worker.ts:87-92`, `content-publish-worker.ts:41-46`, `content-publish-worker.ts:54-59`

Les instances `new Queue(...)` créées inline dans les workers n'ont pas de `defaultJobOptions`. Les jobs enqueués depuis ces instances n'héritent pas du retry/backoff global. Migrer vers `import { contentGenQueue } from "@/server/queue/queues"` ou au minimum ajouter `defaultJobOptions: { attempts: 3, backoff: { type: "exponential", delay: 5000 } }`.

### P1-2 — Aucune DLQ ni replay automatique

Pas de queue `*-dlq` ni de cron `*/30 * * * *` qui replay les jobs `failed` récents (`retryAllFailed()` ou similaire). Les fails définitifs restent figés dans Redis sans alerting structuré par queue (seulement par type de contenu via `alertBatchFail` qui check les 5h).

### P1-3 — concurrency content-gen non DB-managed

`content-gen-worker.ts:641-652` : *"V1 concurrency 5 hardcoded — V2 DB-managed"* mais `ContentGenConfig.workers_concurrency` n'est jamais lu. Pour scale-down (économiser quota OpenAI), Will ne peut pas réduire la concurrence via admin sans redéploiement.

### P1-4 — Backpressure absente sur orchestrateur

`content-orchestrator-worker.ts` n'évalue pas `contentGenQueue.getWaitingCount()` avant d'enqueuer. Si Redis contient déjà 5000 jobs waiting (ex: après un restart), le prochain tick ajoute `tickBudget` (20+) jobs supplémentaires sans cap.

### P1-5 — removeOnComplete/removeOnFail : incohérence age worker vs queue

Workers content-gen/publish/quality-improver posent `removeOnComplete: { count: 1000 }` (sans `age`) ce qui écrase le `age: 7*24*3600` de `queues.ts`. Les jobs complétés il y a > 7 jours ne sont donc jamais purgés par age (seulement par count). Redis peut saturer si le count 1000 n'est jamais atteint (ex: worker peu chargé).

## Synthèse

L'architecture BullMQ est **solide dans ses fondations** : 22 queues bien séparées par responsabilité, backoff exponentiel global, retry configuré par queue, removeOnFail/Complete présents, kill switch transverse, rate-limit sur les workers I/O critiques (OpenAI, Prisma, IndexNow, Google). La pause campagne est fonctionnelle avec une logique correcte.

Les gaps principaux sont : (1) instanciations Queue en doublon sans config retry dans 5 workers, (2) absence de rate-limit sur les workers Claude image-bank, (3) pas de DLQ/replay automatique, (4) concurrency hardcodée non DB-managed, (5) pas d'isolation priority entre campagnes parallèles.
