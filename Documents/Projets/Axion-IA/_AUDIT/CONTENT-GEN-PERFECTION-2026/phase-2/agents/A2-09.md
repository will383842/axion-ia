### Algorithme chainHash : TROUVÉ

Fichier : `axionia/src/server/content-gen/provenance/provenance-logger.ts` (lignes 34-43)

```ts
computeProvenanceHash(previousHash, promptHash, timestamp):
  SHA-256( previousHash + ":" + promptHash + ":" + timestamp.toISOString() )
  .slice(0, 64)
```

Chaînage correct : chaque enregistrement inclut le `hash` du précédent (`previousHash`). La chaîne part d'une valeur vide `""` pour le premier enregistrement. Vérifiable a posteriori via recalcul SHA-256.

**Point positif** : `hashPrompt()` hache le prompt complet en SHA-256 64-char avant stockage — le contenu du prompt n'est jamais persisté en clair (respect RGPD minimisation).

**Point faible** : le `promptHash` dans `content-publish-worker.ts` (ligne 321) est calculé depuis `${cgJob.contentType}:${cgJob.id}:${article.id}` — pas depuis le contenu réel du prompt envoyé au LLM. Ce hash est donc un identifiant de job, pas une empreinte du prompt IA réel. **L'audit trail est incomplet pour l'AI Act art. 50** (on ne peut pas prouver quel prompt exact a produit quel contenu).

### Garantie insert-only : ABSENTE (formellement)

Aucune contrainte DB `INSERT-ONLY` n'est posée sur `generation_provenance`. Le modèle Prisma ne définit pas de règle `UPDATE` interdite. Aucun trigger PG ou permission REVOKE sur UPDATE/DELETE n'a été trouvé dans les migrations.

Le code applicatif ne fournit que `create` (via `logProvenance`) et `findMany` (via `getProvenanceForArticle`). Pas d'opération UPDATE/DELETE dans le code. Mais une opération SQL directe ou un futur refactor pourraient altérer des enregistrements sans invalider la chaîne (car le hash n'est recalculé que par le code applicatif, pas enforced côté DB).

**Absence de RLS / REVOKE sur la table** : non visible dans les migrations analysées.

### API delete avant 6 ans : RISQUE PRÉSENT

La FK `article_id → articles.id ON DELETE CASCADE` (migration ligne 28-31, schema ligne 980) signifie que toute suppression d'un `Article` via `deleteArticle()` (`article.ts:374`) **CASCADE et détruit les enregistrements `generation_provenance` associés**. Il n'existe pas de mécanisme de rétention séparé pour protéger ces enregistrements pendant 6 ans minimum (AI Act art. 50).

### sanitize-job-data : champs redactés

Fichier : `axionia/src/server/queue/lib/sanitize-job-data.ts`

Le helper couvre exhaustivement :
- **Secrets API** : SENSITIVE_KEYS inclut `anthropic_api_key`, `openai_api_key`, `mistral_api_key`, `database_url`, `redis_url`, `ip_hash_salt`, `sentry_dsn`, `stripe_secret_key`, `telegram_bot_token`, `indexnow_key` (et leurs variantes)
- **Emails** : EMAIL_KEYS inclut `email`, `author_email`, `user_email`, `contact_email`, `from`, `to`, `recipient` → redaction partielle `x****@domaine.com`
- **Téléphones** : PHONE_KEYS couverts
- **Patterns regex** : sk-ant-…, Bearer …, JWT 3-segments, Postgres/Redis URL passwords, hex 32-chars INDEXNOW
- **Profondeur** : cap 6 niveaux, 50 clés/objet, strings tronqués à 2000 chars

**Limitation identifiée** : le helper est appliqué uniquement dans le contexte `Sentry.captureException` (via `captureWorkerError`). Il n'est PAS appliqué aux données stockées dans `ContentGenJob.inputPayload` en DB (champ `Json` Prisma). Si `inputPayload` contenait des PII (ex : email d'un auteur RSS, données saisies manuellement dans un job admin), ces données persisteraient en DB sans redaction.

### Prompts Claude : PII présent ?

**Analyse** : les prompts envoyés au LLM Anthropic (`anthropic.ts`) sont construits à partir de `GenerationRequest` contenant `systemPrompt` + `userPrompt`. Ces prompts contiennent du contenu éditorial (titres, keywords, city slugs) mais **pas de données personnelles directes identifiées dans le code analysé**.

**Risque résiduel non-éliminable sans audit complet des generators** : les generators `blog-from-rss.ts` pourraient inclure des auteurs RSS dans le prompt. Le code de `content-gen-worker.ts` extrait `rssSourceName` de `cgJob.inputPayload` — si ce champ contient un nom de personne physique (ex : "Jean Dupont, journaliste"), il transite vers Anthropic sans DPA signé (décision D-W2 ouverte).

**TTL Redis** : les jobs BullMQ sont purgés via `removeOnComplete: { count: 1000 }` et `removeOnFail: { count: 5000 }` dans content-gen-worker et retention-purge-worker. Pas de TTL temporel explicite sur les jobs Redis (par count uniquement). Les données ne s'accumulent donc pas indéfiniment dans Redis.

## 3. Rétention 6 ans AI Act (12/20)

### Relation Article → GenerationProvenance : CASCADE (CRITIQUE)

Fichier : `axionia/prisma/schema.prisma` (ligne 980) + migration SQL (ligne 30-31) :

```sql
FOREIGN KEY ("article_id") REFERENCES "articles"("id") ON DELETE CASCADE ON UPDATE CASCADE
```

**Toute suppression d'Article détruit les enregistrements GenerationProvenance correspondants.** Le code `deleteArticle()` (`article.ts:374`) effectue un `prisma.article.delete()` sans garde-fou de rétention provenance.

**Résultat** : un admin peut supprimer un article (via l'action admin double-confirm "DELETE") et effacer définitivement la trace de traçabilité AI Act exigée pendant 6 ans. Ce flux est fonctionnellement prévu et documenté.

### Politique purge automatique : ABSENTE pour GenerationProvenance

Fichier : `axionia/src/server/queue/workers/retention-purge-worker.ts`

Le worker purge automatique couvre :
- `activity_logs` : 12 mois
- `submissions` archivées : 24 mois
- `newsletter_subscribers` unsubscribed : 36 mois
- `bookings` cancelled : 12 mois
- `generation_logs` : 12 mois
- `cost_ledger` : 24 mois
- `web_vital_samples` : 6 mois
- `image_usage_logs` : 12 mois

**`generation_provenance` n'est PAS dans la liste des tables purgées.** Pas de purge automatique prévue → la table grossit indéfiniment, ce qui est conforme à l'objectif 6 ans AI Act sur ce plan. **Mais ce silence est involontaire** (aucun commentaire "rétention 6 ans" dans le worker).

### Soft delete Article : ABSENT

Aucun champ `deletedAt` ou `archivedAt` n'a été trouvé sur le modèle `Article` dans `schema.prisma`. Le modèle `KnowledgeEntry` possède `deletedAt` (trouvé dans `knowledge-sitemap.ts:63`), mais pas `Article`.

Résultat : la suppression d'Article est destructive (hard delete) avec CASCADE sur `generation_provenance`.

### Conflit RGPD art.17 × AI Act art. 50

| Axe | Position actuelle |
|---|---|
| RGPD art. 17 droit à l'oubli | Implémenté pour PII utilisateurs (newsletter, bookings, submissions). Non applicable à `generation_provenance` (table technique sans PII personnelle directe). |
| AI Act art. 50 rétention 6 ans | Exige conservation des logs IA. `generation_provenance` non protégé contre DELETE CASCADE. |
| Conflit | Si un utilisateur exerce un droit RGPD (suppression de compte) et que des articles lui sont associés, la cascade peut effacer `generation_provenance`. En pratique Axion-IA est B2B sans compte utilisateur → risque limité, mais non adressé formellement. |

**Lacune principale** : pas de politique documentée de rétention 6 ans sur `generation_provenance`, pas de protection technique contre DELETE CASCADE.

## P0 CRITIQUE (conformité)

### P0-1 : CASCADE DELETE détruit les traces AI Act (BLOQUANT deadline 2026-08-02)

**Fichiers** : `prisma/schema.prisma:980`, `prisma/migrations/20260521120100.../migration.sql:30-31`, `src/server/actions/content-gen/article.ts:374`

La FK `generation_provenance.article_id → articles.id ON DELETE CASCADE` couplée à l'action admin `deleteArticle()` permet de détruire irrémédiablement des enregistrements de traçabilité IA qui doivent être conservés 6 ans (AI Act art. 50). Il n'existe aucune protection ni avertissement.

**Correction requise** : changer `onDelete: Cascade` → `onDelete: Restrict` (ou `SetNull`) sur `GenerationProvenance.article`, et implémenter une logique de soft-delete des Articles ou un mécanisme d'archivage séparé des provenance records avant suppression.

### P0-2 : promptHash ne hash pas le prompt réel envoyé au LLM

**Fichier** : `src/server/queue/workers/content-publish-worker.ts:321`

```ts
const promptHash = hashPrompt(`${cgJob.contentType}:${cgJob.id}:${article.id}`);
```

Le `promptHash` stocké dans `generation_provenance` ne représente pas le contenu réel du prompt LLM. L'AI Act art. 50 exige une traçabilité du contenu généré par IA — un hash de l'ID de job n'est pas une empreinte suffisante pour audit technique. La chaîne de hash elle-même reste correcte (SHA-256 chaîné), mais le champ `promptHash` est sémantiquement vide.

**Correction requise** : passer le `promptHash` réel depuis les providers LLM (anthropic.ts, openai.ts) jusqu'au `logProvenance()`. La logique `hashPrompt(systemPrompt + userPrompt)` existe dans le module mais n'est pas utilisée au bon endroit.

### P0-3 : DPA Anthropic non signé — données RSS potentiellement PII transitent

**Contexte** : décision D-W2 ouverte (DPA Anthropic non signé). Le provider `anthropic.ts` envoie des prompts à l'API Anthropic. Si des noms d'auteurs RSS ou d'autres PII se trouvent dans `inputPayload.rssSourceName` ou le contenu de l'article, ils transitent vers Anthropic sans encadrement contractuel RGPD.

**Correction requise** : signer le DPA Anthropic (action Will) ET ajouter un filtre PII sur le contenu envoyé aux providers (redaction `author_name`, `contact_*` avant injection prompt).

## P1 identifiés

### P1-1 : Absence de politique documentée de rétention 6 ans sur generation_provenance

Le worker `retention-purge-worker.ts` ne mentionne pas `generation_provenance`. Il manque :
1. Un commentaire explicite "AI Act art. 50 — retention min 72 mois" dans le worker
2. Une variable env `RETENTION_GENERATION_PROVENANCE_MONTHS` avec valeur min 72
3. Une garde dans le worker qui refuse de purger avant 72 mois si la var est < 72

### P1-2 : Pas de trigger/RLS INSERT-ONLY sur generation_provenance

Sans contrainte DB, un opérateur avec accès direct à Postgres peut modifier des enregistrements sans invalider la chaîne (le hash n'est pas re-vérifié automatiquement). Recommandation : ajouter un trigger PG `BEFORE UPDATE OR DELETE ON generation_provenance → RAISE EXCEPTION` ou un rôle DB read-only sur cette table.

### P1-3 : Article sans soft-delete → hard delete + CASCADE

Recommandation : ajouter `deletedAt DateTime? @map("deleted_at")` sur le modèle `Article` et transformer `deleteArticle()` en soft-delete. Le CASCADE sur `generation_provenance` serait ainsi protégé naturellement.

### P1-4 : Initialisation Anthropic au niveau module (fragilité)

`image-seo-enrichment.service.ts:34` et `image-translation.service.ts:27` instancient `new Anthropic({ apiKey: env.ANTHROPIC_API_KEY })` au niveau module. Si la clé est absente, le service crash à l'import. Risque de fuite du message d'erreur contenant le nom de la variable en logs. Pattern lazy `getClient()` préférable (comme dans `anthropic.ts:123`).

### P1-5 : Prompt envoyé à Claude via image-bank sans audit trail provenance

Les services `image-seo-enrichment.service.ts` et `image-translation.service.ts` appellent Claude Sonnet pour enrichir les images. Ces appels ne passent pas par `logProvenance()`. Ils ne sont donc pas tracés dans `generation_provenance`. Si AI Act couvre les images IA-enrichies (descriptions générées), ces appels sont hors conformité.
