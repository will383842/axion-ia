## 1. FOR UPDATE SKIP LOCKED atomicité (15/25)

### Requête exacte trouvée

Fichier : `axionia/src/server/content-gen/keyword-selector.ts`, lignes 91–103

```sql
UPDATE keywords
SET usage_count = usage_count + 1,
    last_used_at = NOW()
WHERE id = (
  SELECT id FROM keywords
  WHERE vertical = ${vertical}
  ORDER BY last_used_at ASC NULLS FIRST, usage_count ASC, term ASC
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING term
```

### Transaction wrapping : ABSENT (GAP P0)

La requête est exécutée via `prisma.$queryRaw<>()` **directement**, sans être enveloppée dans un bloc `prisma.$transaction()`. Il s'agit d'une requête `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED)` qui est atomique au niveau SQL (un seul statement), ce qui est correct pour empêcher la double sélection entre workers. Toutefois :

- **Pas de `$transaction()` wrapper** : si la suite du traitement dans `content-gen-worker.ts` échoue après la réservation du keyword, le keyword reste marqué `usage_count+1` et `last_used_at=NOW()` sans rollback possible. Il n'y a aucun mécanisme pour remettre le keyword "disponible".
- Le pattern `UPDATE ... RETURNING term` est **techniquement atomique** (une seule instruction Postgres), donc deux workers concurrents ne peuvent pas sélectionner le même keyword. Sur ce point le verrou est correct.
- La durée du verrou SQL est **minimale** (libéré dès la fin du `UPDATE`). Le `FOR UPDATE SKIP LOCKED` est dans le sous-SELECT, pas dans une transaction longue.

### Mécanisme libération lock si crash : ABSENT (GAP P0)

- Il n'existe **aucun champ** `lockedUntil`, `locked_by`, `locked_until` ou `lockExpires` dans le modèle `Keyword` (schéma `prisma/schema.prisma` lignes 3210–3229 confirmé — champs : `id`, `term`, `termNormalized`, `vertical`, `searchIntent`, `isLongTail`, `isLocal`, `cityIds`, `searchVolume`, `difficulty`, `clusterId`, `usageCount`, `lastUsedAt`, `createdAt`).
- Si un worker crashe après `selectKeyword()` mais avant de générer l'article, le keyword est consommé (`usage_count` incrémenté, `last_used_at` mis à jour) sans produire d'article. Il n'y a aucun cleanup automatique.
- Pas de cron/job de nettoyage de keywords "consommés sans production".

### Test logique 3 workers simultanés (vertical = "audits")

- Worker W1 : `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` → prend KW-id-001 (lock row-level Postgres)
- Worker W2 : tente le même — KW-id-001 est locké → SKIP → prend KW-id-002
- Worker W3 : prend KW-id-003
- **Résultat : pas de doublon côté sélection SQL** — le pattern UPDATE+RETURNING est correct.
- **MAIS** : le filtre `WHERE vertical = ${vertical}` ne filtre PAS par `campaignId`. Deux campagnes différentes (Paris×formation = "interventions_formations", Lyon×audit = "audits") utilisent des verticals différentes → isolation naturelle des pools. Si deux campagnes partagent la même vertical, elles **piochent dans le même pool** de keywords.

### Détail scoring

| Critère | Points |
|---------|--------|
| `FOR UPDATE SKIP LOCKED` présent et fonctionnel | +8 |
| UPDATE atomique (libération lock instantanée) | +5 |
| Absence de `$transaction()` wrapper pour rollback | -5 |
| Absence mécanisme `lockedUntil` / cleanup crash | -5 |
| Fallback in-memory non thread-safe (Map partagée process) | -3 (noté en P1) |

**Score dimension 1 : 15/25**

## 2. Isolation campagnes (14/20)

### Filtre campaignId sur SKIP LOCKED : ABSENT

La requête dans `keyword-selector.ts` filtre uniquement par `vertical` (`WHERE vertical = ${vertical}`). Il n'y a **aucun filtre `campaignId`** dans la sélection de keyword. La table `Keyword` n'a pas de colonne `campaign_id` (schéma confirmé). Deux campagnes de même vertical partagent le même pool de keywords.

**Cas scénario test :**
- Campagne A (Paris × formation) → vertical `interventions_formations`
- Campagne B (Lyon × audit) → vertical `audits`
→ Pools distincts car verticals différentes : **pas de collision dans ce scénario précis**.
→ Si deux campagnes avaient la même vertical : collision possible.

### Articles portent bon campaignId

Le `ContentGenJob` créé par l'orchestrateur (`content-orchestrator-worker.ts` ligne 265) reçoit `campaignId: campaign.id`. L'article publié (`content-publish-worker.ts`) crée l'Article via `cgJob.outputBlogPostId` mais **l'Article lui-même n'a pas de champ `campaignId`** (schéma `model Article` lignes 874–959 : aucun champ `campaignId`). La traçabilité campaign→article passe uniquement par `ContentGenJob.campaignId` + `Article.generatedByJobId`.

### Schéma queues BullMQ : PARTAGÉES (GAP P1)

- Queue unique `"content-gen"` pour tous les jobs de toutes les campagnes (`QUEUE_NAME = "content-gen"` dans `content-gen-worker.ts` ligne 125).
- L'orchestrateur enqueue dans `"content-gen"` sans discriminant de campagne côté BullMQ.
- Les 5 workers concurrents (`concurrency: 5`) pickent en round-robin sans distinguer les campagnes.
- **Conséquence** : une campagne avec 200 jobs peut monopoliser les 5 workers et starver une campagne avec 2 jobs.
- Pas de queues dédiées par campagne, pas de priority différenciée par campagne.

### Idempotency key cross-campaign

La clé d'idempotence est `hash(campaignId + slotIndex + contentType + anchorVilleSlug)` (lignes 249–255 orchestrateur). Elle garantit qu'un re-tick de l'orchestrateur ne duplique pas les jobs. Elle n'empêche pas la contention entre campagnes sur la queue partagée.

**Score dimension 2 : 14/20**

## 3. pauseCampaign() exactitude (13/15)

### Code exact avec fichier:ligne

Fichier : `axionia/src/server/actions/content-gen/coverage.ts`, lignes 219–273

```typescript
export async function pauseCampaign(id: string): Promise<void> {
  const session = await requireAdmin();
  // 1. Flip campaign → "paused"
  await prisma.coverageCampaign.update({
    where: { id },
    data: { status: "paused", pausedAt: new Date() },
  });

  // 2. Charge jobs "queued" de la campagne (take: 5000)
  const queuedJobs = await prisma.contentGenJob.findMany({
    where: { campaignId: id, status: "queued" },
    select: { id: true },
    take: 5000,
  });

  // 3. Pour chaque job queued → getJob("gen-<id>") → si waiting/delayed/
  //    waiting-children/prioritized → remove()
  if (queuedJobs.length > 0) {
    const queue = getContentGenQueue();
    if (queue) {
      for (const job of queuedJobs) {
        const bullJob = await queue.getJob(`gen-${job.id}`);
        if (bullJob) {
          const state = await bullJob.getState();
          if (state === "waiting" || state === "delayed" ||
              state === "waiting-children" || state === "prioritized") {
            await bullJob.remove();
          }
        }
      }
    }
  }
  // 4. logActivity + revalidatePath
}
```

### Jobs active : comportement documenté

**Les jobs `active` (en cours de traitement par un worker) ne sont PAS supprimés.** Le commentaire ligne 256 est explicite : "Job actif ou introuvable — ignore, le worker gère via kill_switch." Le test unitaire `pause-campaign-b2.spec.ts` (ligne 128) confirme ce comportement : `remove()` n'est appelé que pour le job en état `"waiting"`, pas pour celui en `"active"`.

**Conséquence** : après `pauseCampaign()`, entre 1 et 5 articles peuvent encore être générés par les workers actifs. Acceptable comme comportement "graceful stop" mais doit être documenté pour Will.

### Keywords LOCKED : libérés au pause ?

**NON.** `pauseCampaign()` ne contient aucune logique de libération de keyword. Comme il n'existe pas de champ `lockedUntil` / `locked_by` sur la table `Keyword`, il n'y a rien à libérer. Les keywords déjà consommés par des jobs en cours restent marqués `usage_count+1`. C'est un comportement acceptable (la rotation `lastUsedAt` ASC les déprioritisera naturellement) mais il n'y a pas de reset explicite.

### Cas edge 50 jobs waiting

La boucle `for (const job of queuedJobs)` traite les jobs **séquentiellement** (pas en parallèle). Pour 50 jobs, cela implique 50 appels Redis `getJob()` + 50 `getState()` + jusqu'à 50 `remove()` en séquence. Avec un Redis local ≈ 1ms/op → ~150ms. Avec Redis réseau ≈ 5ms/op → ~750ms. Acceptable pour 50 jobs. Pour 5000 jobs (limite `take: 5000`), cela peut prendre 5–25 secondes — **risque timeout Server Action Next.js (default 30s)**.

**Score dimension 3 : 13/15**

## 4. Cross-campaign pollution (5/10)

### Protection DB (NOT NULL campaignId sur Article) : ABSENTE (GAP P0)

Le modèle `Article` (schéma lignes 874–959) **n'a pas de champ `campaignId`**. La traçabilité campaign→article passe par `ContentGenJob.campaignId` (nullable — `String?` ligne 2909). `ContentGenJob.campaignId` est nullable (`?`) car les pipelines RSS directs (pipeline 2) n'ont pas de campagne parente.

- `Article.generatedByJobId` est nullable (`String?` ligne 901).
- Il n'existe donc aucune contrainte `NOT NULL` au niveau Article garantissant l'appartenance à une campagne.
- La pollution est possible si un bug de routing envoie un job de campagne A dans le pipeline de campagne B : l'Article résultant sera taggué `generatedByJobId` du bon job, mais aucune contrainte DB n'empêche l'erreur.

### Check worker avant publish : ABSENT

Le `content-publish-worker.ts` ne vérifie pas la cohérence `campaignId` avant de publier. Le flux est :
1. `ReviewQueue.jobId` → `ContentGenJob` → `outputJsonRaw`
2. Création `Article` sans vérification que `cgJob.campaignId` est cohérent.

Il n'y a pas de contrôle du type "si cette ReviewQueue appartient à la campagne X, vérifier que le job est bien de la campagne X".

### Mécanisme de protection existant (partiel)

L'idempotency key `hash(campaignId + slotIndex + contentType + anchor)` sur `ContentGenJob.idempotencyKey` (champ `@unique`) empêche la création de doublons de jobs pour une même campagne. Cela constitue une protection partielle contre la re-génération accidentelle, mais ne protège pas contre la cross-contamination de contenu entre campagnes.

### Score par critère

| Critère | Points |
|---------|--------|
| Article.campaignId NOT NULL en DB | 0/3 (absent) |
| ContentGenJob.campaignId présent (nullable) | +2 |
| Check worker avant publish campaignId | 0/3 (absent) |
| Idempotency key inter-campagne robuste | +3 |

**Score dimension 4 : 5/10**

## Scénario test logique 3 workers × 2 campagnes

**Configuration :**
- Campagne A : Paris × formation (200 keywords, vertical `interventions_formations`)
- Campagne B : Lyon × audit (150 keywords, vertical `audits`)
- 3 workers `content-gen` (concurrency 5 = 15 slots max simultanés)

### Simulation tick orchestrateur (toutes les 15 min)

```
tickBudget = dailyBatchSize (ex: 20)
runningCampaigns = [CampagneA, CampagneB]
perCampaignTick = floor(20 / 2) = 10

CampagneA : toEnqueue = min(10, 200) = 10 jobs créés, campaignId=A
CampagneB : toEnqueue = min(10, 150) = 10 jobs créés, campaignId=B
→ 20 jobs dans queue "content-gen" partagée
```

### Simulation workers parallèles

**Sélection keywords :**
- W1 picks job-A1 (campaignA) → selectKeyword({vertical:"interventions_formations"}) → KW-F001
- W2 picks job-B1 (campaignB) → selectKeyword({vertical:"audits"}) → KW-A001
- W3 picks job-A2 (campaignA) → selectKeyword({vertical:"interventions_formations"}) → KW-F002
→ **Pas de doublon keywords** (verticals distinctes dans ce scénario)

**Cross-campaign contamination :**
- job-A1 produit article avec `generatedByJobId=job-A1.id` (campaignId=A)
- job-B1 produit article avec `generatedByJobId=job-B1.id` (campaignId=B)
→ **Pas de contamination directe** car le campaignSector est lu depuis `dbJob.campaignSector` (ligne 247 content-gen-worker) qui est résolu depuis le `ContentGenJob` en DB (correctement scoped).

**RISK identifié :**
- Si les deux campagnes avaient la même vertical (ex: deux campagnes "audits" Paris et Lyon), elles **partageraient le même pool de 150 keywords**. Un keyword pourrait être utilisé par les deux campagnes au même tick (pas de filtre campaignId dans SKIP LOCKED).
- La queue partagée sans priorité par campagne peut créer du **starvation** : si campagne A a 1000 jobs en waiting et campagne B en a 10, les 3 workers vont quasi-exclusivement traiter A.

### Résultat simulé

| Test | Résultat | Justification |
|------|----------|---------------|
| Double sélection keyword cross-worker (même vertical) | **OK** | SKIP LOCKED atomique SQL fonctionne |
| Isolation keywords inter-campagnes (verticals distinctes) | **OK** | Filtre `WHERE vertical` suffit |
| Isolation keywords inter-campagnes (même vertical) | **RISK** | Aucun filtre campaignId sur keyword |
| Cross-contamination article (mauvais campaignId sur Article) | **OK partiel** | Traçabilité via generatedByJobId correcte, pas de contrainte DB |
| Starvation campagne B si campagne A sature la queue | **RISK** | Queue partagée sans priority différenciée |
| Comportement si crash worker mid-job | **RISK** | Keyword consommé sans rollback, aucun lockedUntil |

**Verdict global : RISK** — Le système fonctionne correctement dans le cas nominal (campagnes de verticals différentes, workers stables), mais présente des risques structurels en cas de campagnes de même vertical, de crash worker, ou de déséquilibre de charge.

## P0 identifiés

### P0-1 : Absence de rollback keyword si crash worker
**Fichier :** `keyword-selector.ts:91–103`
**Impact :** En cas de crash worker après `selectKeyword()` mais avant génération, le keyword est consommé (usage_count incrémenté, lastUsedAt mis à jour) sans production d'article. Accumulation silencieuse de keywords "brûlés". Sur 200 keywords et 10% crash rate → ~20 keywords perdus par cycle.
**Fix reco :** Ajouter `lockedUntil` + `lockedBy` sur table `Keyword`. Cron cleanup toutes les 5 min pour libérer les locks expirés (>15min). Wrapper dans `$transaction()` avec rollback si l'article n'est pas créé.

### P0-2 : Aucune contrainte NOT NULL / FK garantissant Article.campaignId
**Fichier :** `prisma/schema.prisma:874–959` + `content-publish-worker.ts:239–301`
**Impact :** Un bug de routing (ex: ReviewQueue pointe sur un job d'une campagne déjà annulée) peut publier un article sans traçabilité campaign. Impossible d'auditer post-facto "quels articles ont été produits par quelle campagne" directement depuis la table `article`.
**Fix reco :** Ajouter `campaignId String? @map("campaign_id")` sur `Article` avec FK vers `CoverageCampaign`. Propager depuis `ContentGenJob.campaignId` lors de la création Article dans publish-worker.

## P1 identifiés

### P1-1 : Fallback in-memory non thread-safe en cas de multi-process
**Fichier :** `keyword-selector.ts:41–55`
**Impact :** La Map `inMemoryCounters` est locale au process Node.js. Si plusieurs instances (Coolify = N replicas ou N worker threads séparés), chaque instance a son propre compteur → duplication de keywords en mode fallback. En production single-process, ce P1 est dormant.
**Fix reco :** Fallback Redis ou aléatoire pur (sans état partagé) pour le fallback in-memory.

### P1-2 : Queue partagée sans priorité par campagne → starvation possible
**Fichier :** `content-orchestrator-worker.ts:64–70` + `content-gen-worker.ts:650`
**Impact :** Queue unique `"content-gen"` pour toutes campagnes. Une campagne avec 5000 jobs peut starver une campagne prioritaire avec 10 jobs.
**Fix reco :** Utiliser le champ `priority` de BullMQ différencié par campagne, ou créer des queues `content-gen-campaign-{id}` dédiées avec round-robin entre workers.

### P1-3 : pauseCampaign() séquentiel — timeout risque pour > 1000 jobs
**Fichier :** `coverage.ts:240–258`
**Impact :** La boucle séquentielle sur les jobs `queued` peut prendre > 30s si > 1000 jobs (Redis latence réseau ~5ms/op × 3 ops/job = 15s pour 1000 jobs). Server Actions Next.js timeout = 30s par défaut.
**Fix reco :** Utiliser `Promise.all()` avec concurrence limitée (ex: `p-limit(50)`) ou `obliterate()` filtré si BullMQ le supporte, ou job background pour les purges > 500 items.

### P1-4 : Keyword pool partagé si deux campagnes ont la même vertical
**Fichier :** `keyword-selector.ts:96–100`
**Impact :** Deux campagnes `audits` (Paris et Lyon) partagent les 150 keywords `audits`. Sans filtre campaignId, les mêmes keywords sont distribués entre les deux campagnes. Risque de contenu trop similaire si le keyword influence fortement le titre/contenu.
**Fix reco :** Soit ajouter un filtre optionnel `campaignId` sur la sélection keyword, soit documenter que c'est intentionnel (rotation équitable cross-campagnes de même secteur).

### P1-5 : Jobs active non arrêtés au pause — fenêtre de production non contrôlée
**Fichier :** `coverage.ts:254–256`
**Impact :** Entre 1 et 5 articles peuvent être générés après `pauseCampaign()` (concurrency 5). Acceptable en général mais problématique si la raison du pause est "contenu non conforme AI Act" (où chaque article supplémentaire aggrave la situation).
**Fix reco :** Activer le kill_switch global temporairement + pause campagne comme pattern de pause d'urgence, ou ajouter une vérification `campaign.status === 'running'` en début de `processJob()` dans le content-gen-worker.
