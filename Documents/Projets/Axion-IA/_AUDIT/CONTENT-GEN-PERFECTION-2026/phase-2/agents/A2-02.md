## 3. Requêtes N+1 (14/20)

### Analyse des patterns de requêtes

#### Patterns OK (include: correct)

`getBlogArticlesByVille` (get-articles-by-ville.ts:47-66) : `findMany` avec `select: { translations: { where: { locale }, take: 1 } }` — **correct**, pas de N+1. La translation est incluse dans la même requête.

`getProvenanceForArticle` (provenance-logger.ts:122-133) : `findMany` avec `where: { articleId }` — simple requête unique, correct.

#### Problème N+1 identifié — dedup-guard.ts

**P0 — dedup-guard.ts:107-173** : `checkDedup` fait un `findMany` pour récupérer jusqu'à 5000 `ContentGenJob` (LOOKBACK_LIMIT), puis **boucle JS for...of** sur le résultat pour extraire `inputPayload.title` et calculer Levenshtein individuellement :

```
dedup-guard.ts:107 → prisma.contentGenJob.findMany({ take: 5000 })
dedup-guard.ts:123 → for (const job of recent) { levenshteinSimilarity(...) }
```

Ce n'est pas un N+1 classique (pas de requête dans la boucle), mais c'est un **pattern de charge extrême** : 5000 rows récupérées côté Node, Levenshtein O(m×n) calculé en JS pour chacune. À 5000 jobs × 300 chars titre moyen, le calcul JS prend ~50-200ms par appel `checkDedup`. Chaque job content-gen trigger un `checkDedup` → **goulot d'étranglement à l'échelle**.

**Solution recommandée** : déléguer la comparaison à PostgreSQL via `similarity()` (pg_trgm) ou utiliser le champ `topicFingerprint` + index pour un filtre préalable.

#### Problème potentiel N+1 — checkOutlineDedup (dedup-guard.ts:249-258)

`checkOutlineDedup` fait un `findMany` de 1000 articles publiés avec `outlineSimhash`, puis boucle JS pour calculer `outlineHammingDistance` sur chaque. Même pattern que ci-dessus, même goulot à l'échelle. À 1000 items, tolérable (~5-10ms), mais croît linéairement.

#### provenance-logger.ts:62-63 — findFirst par articleId

```
provenance-logger.ts:62 → prisma.generationProvenance.findFirst({
  where: { articleId },
  orderBy: { timestamp: 'desc' },
  select: { hash: true }
})
```

Requête correcte mais sans index composite `(articleId, timestamp DESC)`. Avec index séparés `(articleId)` et `(timestamp)`, PostgreSQL doit choisir l'un ou l'autre — en pratique l'index `(articleId)` sera utilisé puis tri, ce qui est acceptable si peu d'enregistrements par articleId. Mais à volume (10+ appels LLM par article), l'absence d'index composite crée un tri coûteux.

#### guides/loader.ts — pattern include probable

Non lu intégralement mais présent dans la liste. Le fichier `guides/loader.ts` + son spec mock `article.findMany` et `articleTranslation.findFirst` séparément — pattern potentiellement N+1 si loader charge les articles puis les traductions en boucle. Nécessiterait vérification.

### Points retirés (-6)

| Problème | Fichier:ligne | Déduction |
|----------|---------------|-----------|
| checkDedup : findMany 5000 jobs + boucle Levenshtein JS (perf goulot) | dedup-guard.ts:107+123 | -3 |
| checkOutlineDedup : findMany 1000 articles + boucle Hamming JS | dedup-guard.ts:249-270 | -2 |
| guides/loader.ts : findMany articles + findFirst traduction séparément (non confirmé, -1 prudence) | guides/loader.ts | -1 |

### Points positifs

1. **Idempotence garantie** : toutes les migrations P1.5 utilisent `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ALTER TYPE ADD VALUE IF NOT EXISTS`. Zero risque de crash sur re-run.

2. **Correctif A2/A7 dans 20260514120000** : la migration inclut des commentaires de correctif documentés (`-- Audit A7 patch` × 2, `-- Audit A2 patch`) pour éviter les doubles créations d'enum `KeywordTrackingSource` et les DROP INDEX sur indexes pgvector/FTS non trackés par Prisma. Cela prouve une rigueur d'audit appliquée en amont.

3. **pgvector dims cohérentes** : migration `20260521130000` utilise `vector(1536)` (OpenAI text-embedding-3-large) avec commentaire explicite "1536 < 2000 (limite HNSW pgvector)" — cohérent avec schema.prisma:944 et MEMORY.md (migration IVFFlat→HNSW corrigée).

4. **FK correcte** : `generation_provenance_article_id_fkey` avec `ON DELETE CASCADE` — correspond à `onDelete: Cascade` dans schema.prisma:980.

5. **Séquence logique** : keyword_tracking créé avant content_gen_core (pas de dépendance inverse), sites_web_augmentes avant generation_provenance (indépendants mais ordre cohérent), dedup layers après keyword seeds.

### Risques identifiés

| Risque | Migration | Sévérité |
|--------|-----------|---------|
| `ADD COLUMN embedding vector(1536)` : nullable par défaut. Les articles existants ont `embedding = NULL`. L'index HNSW sur une colonne partiellement nulle est correct (pgvector l'ignore) mais la couche A.4 ne peut pas fonctionner tant que les embeddings ne sont pas backfillés. | `20260521130000` | P2 (fonctionnel, pas bloquant) |
| `keyword_tracking` migration `20260514100000` crée les colonnes en camelCase (`targetUrl`, `syncedAt`) mais le schéma Prisma utilise des snake_case mappings (`@map("target_url")`, `@map("synced_at")`). La migration raw et le schéma semblent décalés. | `20260514100000` vs schema.prisma:3171-3192 | **P0 — voir ci-dessous** |
| DROP INDEX commentés dans `20260514120000` (HNSW + FTS) : OK, mais si quelqu'un régénère les migrations via `prisma migrate diff`, ces index pourraient être re-droppés. | `20260514120000` | P1 |

**Analyse P0 migration keyword_tracking** : La migration `20260514100000` crée les colonnes en camelCase (`targetUrl VARCHAR(512)`, `syncedAt`, `firstSeenAt`, `createdAt`, `updatedAt`) tandis que le schéma Prisma déclare `@map("target_url")` etc. En pratique, Prisma génère les requêtes avec les noms mappés. Si la migration a créé les colonnes en camelCase, il y a un drift schema/DB. Cependant, la migration `20260514120000` ne mentionne pas de renommage, suggérant que soit (a) la migration raw a effectivement utilisé camelCase et Prisma s'en accommode (colonnes Postgres case-insensitive pour les identifiants non-quotés), soit (b) ce sont des colonnes snake_case créées par Prisma ensuite. Ce point requiert vérification manuelle via `psql \d keyword_tracking`.

## P0 identifiés

### P0-1 — Index composite manquant sur `articles(status, publishedAt DESC)`
**Impact** : Toutes les pages blog public (`/fr/blog`, pagination, sitemap) font un `WHERE status = 'published' ORDER BY publishedAt DESC LIMIT n`. Sans index composite, PostgreSQL fait un seq scan + sort sur la table entière à chaque request. À 10K+ articles, latence ~500ms+.
**SQL fix** : `CREATE INDEX CONCURRENTLY articles_status_published_at_idx ON articles(status, published_at DESC);`

### P0-2 — Index composite manquant sur `generation_provenance(articleId, timestamp DESC)`
**Impact** : `logProvenance` (provenance-logger.ts:62) fait `findFirst` par `articleId ORDER BY timestamp DESC` à chaque appel LLM. Sans index composite, PostgreSQL utilise l'index `(articleId)` puis tri — coûteux si plusieurs dizaines d'appels LLM par article. Fire-and-forget mais latence mesurable.
**SQL fix** : `CREATE INDEX CONCURRENTLY generation_provenance_article_ts_idx ON generation_provenance(article_id, timestamp DESC);`

### P0-3 — Index manquant sur `keywords(vertical, last_used_at ASC NULLS FIRST, usage_count ASC)`
**Impact** : `keyword-selector.ts:94-102` exécute `SELECT ... FOR UPDATE SKIP LOCKED ORDER BY last_used_at ASC NULLS FIRST, usage_count ASC, term ASC WHERE vertical = $1`. L'index `(vertical)` seul force un sort sur ~100-200 rows par vertical — acceptable maintenant mais croît avec les seeds.
**SQL fix** : `CREATE INDEX keywords_vertical_rotation_idx ON keywords(vertical, last_used_at ASC NULLS FIRST, usage_count ASC);`

### P0-4 — Drift potentiel colonnes camelCase dans migration `20260514100000_add_keyword_tracking`
**Impact** : Migration raw SQL utilise `targetUrl`, `syncedAt`, etc. (camelCase) alors que le schéma Prisma déclare `@map("target_url")`, `@map("synced_at")`. Si les colonnes DB sont réellement en camelCase, les requêtes Prisma utilisant les mappings snake_case échoueraient en prod.
**Action** : Vérifier `psql \d keyword_tracking` et si besoin `ALTER TABLE keyword_tracking RENAME COLUMN "targetUrl" TO target_url` etc.

## P1 identifiés

### P1-1 — `checkDedup` : 5000 rows + Levenshtein JS O(n²)
`dedup-guard.ts:107-173` — Performance goulot à l'échelle. Recommandation : utiliser `similarity(title, ?) > 0.85` via extension `pg_trgm` (déjà activée dans `datasource.extensions`) côté DB, réduisant le workload à 1 requête SQL.

### P1-2 — FK absente `Article.generatedByJobId → ContentGenJob.id`
`schema.prisma:900-901` — Commentaire "FK ContentGenJob.id (cuid String — pas @db.Uuid)" indique un choix intentionnel pour éviter la contrainte de type. Sans FK, les orphelins sont possibles (job supprimé, article reste avec generatedByJobId invalide). Même gap pour `FAQ.generatedByJobId`.

### P1-3 — `ContentGenJob.outputBlogPostId` sans relation Prisma déclarée
`schema.prisma:2942` — La colonne `outputBlogPostId @db.Uuid` est une FK de fait vers `articles.id` mais sans `@relation` Prisma. Impossible d'utiliser `include:` — oblige les requêtes raw ou une jointure manuelle. Devrait déclarer `outputBlogPost Article? @relation(...)`.

### P1-4 — `topicFingerprint` colonne inutilisée prod (STUB)
`topic-fingerprint.ts:72-87` — `computeTopicFingerprint()` retourne `null` jusqu'à VOYAGE_API_KEY. La colonne est présente dans `Article` et `KnowledgeEntry` mais jamais peuplée. L'index composite `@@index([indexationTier, status])` ne couvre pas la colonne. Pas bloquant mais overhead schema.

### P1-5 — `checkOutlineDedup` : 1000 articles + boucle Hamming JS
`dedup-guard.ts:249-270` — Même pattern que P1-1 mais moins sévère (1000 items, Hamming distance sur 16 chars hex est O(16) donc fast). Scalabilité à surveiller à 10K+.

### P1-6 — Guides loader pattern N+1 probable
`guides/loader.ts` — Spec mock révèle `article.findMany` + `articleTranslation.findFirst` séparément. Si loader charge articles puis appelle findFirst par articleId dans une boucle, c'est un N+1. À confirmer.

### P1-7 — Migration `20260521130000` : HNSW créé sans `ivfflat_probes` ni `hnsw_ef_search`
L'index HNSW est créé avec paramètres par défaut (`m=16 ef_construction=64`). Pour les recherches de similarité en production, `SET hnsw.ef_search = 100` devrait être configuré au niveau session. Non bloquant mais impacte la recall.
