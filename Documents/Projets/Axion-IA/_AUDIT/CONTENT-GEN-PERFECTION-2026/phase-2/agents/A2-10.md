### P2-2 — Couche 4 embeddings pre-publish wiring (~3-4h, CONDITIONNEL)

**État actuel dans le code** :

La couche 4 OpenAI embeddings est **partiellement implémentée mais non câblée dans le pipeline publish** :
- `openai-embedder.ts` : embed() fonctionnel, daily cap, fail-soft — complet.
- `embedding-similarity.ts` : cosineSimilarity + classifyDedupVerdict — complet et testé.
- `content-publish-worker.ts` : **AUCUN appel à embed() ni à classifyDedupVerdict**. Le worker pose l'outlineSimhash (couche 3) mais ne fait pas de check cosine pre-publish.
- `content-similarity-monitor-worker.ts` : worker de monitoring existant — pas audité ici.

**Gap exact** : Le pipeline pre-publish manque du check cosine. Séquence cible non implémentée :
1. Appel `embed(buildEmbeddingInput({title, metaDescription, bodyText}))` dans `content-publish-worker.ts`.
2. Query pgvector cosine `<=>` sur `Article.embedding` (colonne existante dans le schema ?).
3. `classifyDedupVerdict({similarity, duplicateThreshold: 0.85, similarThreshold: 0.80})`.
4. Si `duplicate` → reject publish ; si `similar` → warn dans GenerationLog.
5. Persist l'embedding sur l'Article créé.

**Condition bloquante** : `OPENAI_EMBEDDINGS_ENABLED=true` doit être posé dans Coolify par Will. Sans ce flag, `embed()` retourne `null` (fail-soft explicite ligne 64 openai-embedder.ts). Le wiring peut être codé S+6 mais sera no-op jusqu'à l'activation.

**Effort réel réévalué** : 3-4h (vs 4-6h estimé P1.5). L'infrastructure est déjà là (openai-embedder.ts + embedding-similarity.ts prêts). Le travail restant = wiring dans publish-worker + vérifier la colonne `Article.embedding` dans le schema Prisma + migration si absente.

### P2-3 — Frontend Article.featuredImage rendu avec `<Image>` (~2-3h, GO)

La page blog `src/app/[locale]/blog/[slug]/page.tsx` (412 lignes auditées) **ne rend PAS du tout l'image hero**. Ni `<Image>` next/image, ni `<img>`, ni `featuredImage` dans tout le JSX de la page. Le champ est :
- Bien persisté dans la DB par `content-publish-worker.ts` (ligne 269 : `featuredImage: heroImageFilePath`).
- Bien renvoyé par le loader `loader.ts`... **non** : `BlogArticleView` (interface loader.ts lignes 21-36) ne contient pas `featuredImage`. Le loader ne sélectionne pas ce champ.

**Gap exact** :
1. `BlogArticleView` interface → ajouter `featuredImage: string | null`.
2. `loadBlogArticleForView` → projeter `featuredImage` depuis `findArticleBySlug`.
3. `blog/[slug]/page.tsx` → ajouter bloc `<Image>` Next.js avec srcset WebP/AVIF via `<picture>` ou Next.js Image optimisation (LCP impact — hero doit être priority={true}).

**Contrainte Web Vitals** (AGENTS.md) : LCP ≤ 1800ms p75. Le hero image doit être `priority` (preload) sinon risque de régression LCP.

**Effort réel réévalué** : 2-3h (vs 2h estimé P1.5). Le fix est légèrement plus large que prévu car il touche 3 couches (interface + loader + page).
