Ce choix est cohérent et délibéré : text-embedding-3-large supporte la réduction de dimensionnalité via paramètre API `dimensions`. La limite pgvector 2000 dims a été respectée.

### Analyse de la non-présence d'IVFFlat

Puisqu'il n'y a aucun `lists=1` dans le codebase, cette dimension de l'audit est évaluée différemment :

**Impact perf théorique de lists=1 (si IVFFlat avait été choisi) :** Un index IVFFlat avec `lists=1` équivaut à un scan séquentiel complet — zéro bénéfice d'index. Le seuil minimal recommandé est `lists = sqrt(n_rows)`, soit ≈ 100 pour 10 000 lignes. **Ce risque est absent du projet car HNSW est utilisé.**

### Seuil de migration HNSW (informatif)

Pour les index HNSW actuels :
- `m=16, ef_construction=64` : paramètres par défaut pgvector V1, corrects pour < 100k vecteurs.
- Migration recommandée à partir de 100k vecteurs : augmenter `ef_construction` à 128 et `m` à 32 pour meilleure recall.
- Plan sans downtime : `CREATE INDEX CONCURRENTLY ... USING hnsw` avec les nouveaux paramètres, puis `DROP INDEX CONCURRENTLY` de l'ancien.

## 2. IVFFlat vs HNSW 3072 dim (20/20)

### Version pgvector installée

Trouvée dans `migration.sql` (20260514020000, ligne 31) : `pgvector 0.5+` (mention explicite). Confirmé par l'utilisation de l'opérateur `<=>` (cosine distance) dans `dedup-check.ts`.

Version requise pour HNSW : pgvector ≥ 0.5.0 (sorti juillet 2023). Version probablement installée en prod : pgvector 0.7.x ou 0.8.x (image `pgvector/pgvector:pg16`).

### Tableau comparatif IVFFlat vs HNSW pour ce use-case

| Critère | IVFFlat | HNSW |
|---|---|---|
| Limite dimensionnalité | 2000 dims max | 2000 dims max (pgvector < 0.8), illimité ≥ 0.8 |
| Vitesse build index | Rapide (clustering K-means) | Lent (graphe hiérarchique) |
| Vitesse query | Plus rapide (probes configurables) | Plus rapide à recall équivalent |
| Qualité recall | 90-95 % avec probes=10 | 95-99 % avec ef_search=40 |
| RAM peak query | Faible | Modéré |
| RAM index en mémoire | Faible | Élevé (O(m × n)) |
| Downtime rebuild | Requis si `lists` change | Non requis (CONCURRENTLY) |
| `lists=1` anti-pattern | Score total (séquentiel) | N/A |
| Maintenance | Nécessite `VACUUM` pour perf stable | Stable sans maintenance |
| Adapté 1536 dims | OK (< 2000 limite) | OK |
| Adapté 3072 dims (full) | NON (dépasse 2000 limite) | Dépend version pgvector |

### Recommandation motivée

**HNSW est le bon choix pour ce projet — décision correcte.** Raisons :

1. **Recall supérieur** : le pipeline dedup cosine exige une haute précision (faux négatifs = doublons publiés). HNSW recall 95-99 % vs IVFFlat 90-95 %.
2. **Limite dims respectée** : 1536 < 2000. Si Will décide d'activer les 3072 dims natifs, il faudra pgvector ≥ 0.8 ou rester à 1536.
3. **Pas de `lists=1` anti-pattern** : IVFFlat avec `lists` mal configuré est le principal risque cité dans l'audit spec — ce risque est inexistant.
4. **Opérateur `<=>` actif** : `dedup-check.ts` utilise `kemb.embedding <=> $1::vector` (cosine distance) — syntaxe compatible HNSW.

**Recommandation pour upgrade à 3072 dims à terme :** Vérifier version pgvector prod (`SELECT extversion FROM pg_extension WHERE extname='vector'`). Si ≥ 0.8.0 : modifier `OPENAI_EMBEDDING_DIMENSION` à 3072, nouvelle migration `ALTER COLUMN embedding TYPE vector(3072)` + `CREATE INDEX CONCURRENTLY` HNSW. Coût : 2× plus de tokens OpenAI et storage.

## 3. Query plan keyword-selector (17/20)

### Requête exacte trouvée dans le code

`axionia/src/server/content-gen/keyword-selector.ts` (lignes 91-103) — via `prisma.$queryRaw` :

```sql
UPDATE keywords
SET usage_count = usage_count + 1,
    last_used_at = NOW()
WHERE id = (
  SELECT id FROM keywords
  WHERE vertical = ${vertical}
  ORDER BY last_used_at ASC NULLS FIRST, usage_count ASC, term ASC
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING term
```

### Index présents sur la table `keywords`

`axionia/prisma/migrations/20260521120200_add_keywords_table/migration.sql` :
```sql
CREATE UNIQUE INDEX IF NOT EXISTS "keywords_term_key" ON "keywords"("term");
CREATE INDEX IF NOT EXISTS "keywords_vertical_idx" ON "keywords"("vertical");
CREATE INDEX IF NOT EXISTS "keywords_usage_count_last_used_at_idx"
    ON "keywords"("usage_count", "last_used_at");
```

### Analyse atomicité SKIP LOCKED

**Points forts :**
- Pattern `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING term` est le pattern canonique Postgres pour file de travail concurrente. Atomique et correct pour N workers parallèles.
- `FOR UPDATE SKIP LOCKED` évite les deadlocks et les attentes bloquantes : si un worker a déjà locké une ligne, les autres workers passent à la suivante.
- Index `keywords_vertical_idx` sur `vertical` couvre le filtre `WHERE vertical = $1` dans le subquery.

**Problèmes identifiés :**

1. **Index non optimal pour ORDER BY** : La requête trie par `ORDER BY last_used_at ASC NULLS FIRST, usage_count ASC, term ASC`. L'index existant est `(usage_count, last_used_at)` — ordre inversé vs la requête. Le Planner devra probablement faire un sort en mémoire sur les N lignes de la vertical filtrée. Index manquant : `(vertical, last_used_at ASC NULLS FIRST, usage_count ASC)`.

2. **Absence de `lock_timeout`** : La requête `$queryRaw` n'est pas wrappée dans une transaction avec `SET LOCAL lock_timeout`. Avec concurrence 5-10 workers (commentaire dans keyword-selector.ts), si un worker prend du retard, les autres attendent la libération du lock sur la ligne sélectionnée. Risque de cascade de timeouts sous charge élevée.

3. **UPDATE sans transaction explicite** : L'UPDATE est exécuté directement via `$queryRaw` sans `$transaction()`. En cas de crash worker entre l'UPDATE et le retour, le keyword est marqué `last_used_at = NOW()` mais l'article n'est pas généré. Ce n'est pas un P0 (le keyword sera simplement utilisé moins souvent), mais c'est une inconsistance possible.

4. **Pas de `SET LOCAL lock_timeout`** : recommandé à 100ms pour éviter les queues sur workers saturés.

## 4. Backfill strategy (8/15)

### Script backfill : ABSENT

Recherche exhaustive dans `axionia/src/scripts/` : répertoire inexistant ou vide de fichiers backfill. Aucun fichier `backfill*.ts` trouvé dans tout le projet.

Les workers existants (`content-similarity-monitor-worker.ts`, `image-bank-crons-worker.ts`) ne contiennent pas de logique backfill embeddings articles.

**Mention trouvée uniquement dans les commentaires** (`schema.prisma`, ligne 955) :
```
/// Retroactive scan worker possible Sprint S+3 si besoin backfill historique
```
Et dans `topic-fingerprint.ts` : `worker embedding-fill-worker activé` (référence à un worker non encore créé).

### État actuel du pipeline embedding articles

- Colonne `articles.embedding vector(1536)` : nullable, créée en migration 2026-05-21.
- Population : uniquement au moment du publish via `openai-embedder.ts` (si `OPENAI_EMBEDDINGS_ENABLED=true`).
- Flag par défaut : `false` → **zéro embeddings en DB pour les articles existants si flag activé sans backfill préalable.**
- Implication : activation de `OPENAI_EMBEDDINGS_ENABLED=true` sans backfill = couche 4 dedup inopérante sur tout le corpus historique. Seuls les nouveaux articles seront comparés. Les doublons vs articles historiques ne seront pas détectés.

### Risque incohérence flag activé sans backfill

Si Will active `OPENAI_EMBEDDINGS_ENABLED=true` en prod Coolify :
- Nouveaux articles publiés → embedding calculé + stocké en DB.
- Articles existants publiés → `embedding IS NULL` → la requête `<=>` les exclut du corpus dedup.
- Résultat : nouveaux articles peuvent être des doublons proches d'articles historiques sans détection.
- Ce risque est réel et non documenté dans le code (aucun warning au startup).

### Plan backfill recommandé (non implémenté)

Un worker `content-embedding-backfill-worker.ts` devrait :
1. SELECT articles WHERE embedding IS NULL AND status = 'published' ORDER BY published_at DESC LIMIT 50.
2. Pour chaque article : appeler `buildEmbeddingInput()` + `embed()`.
3. UPDATE articles SET embedding = $1::vector WHERE id = $2.
4. Pause 200ms entre batches (rate-limit OpenAI tier 1 = 3000 RPM).
5. Cron : `*/5 * * * *` jusqu'à backfill complet.
6. Idempotent : WHERE embedding IS NULL garantit pas de double facturation.

### Coût estimé OpenAI backfill 10 000 articles

- Modèle : `text-embedding-3-large` avec `dimensions=1536`.
- Tarif : $0.13 / 1M tokens.
- Tokens par article (moyenne `buildEmbeddingInput`) : titre (10 tokens) + meta (20 tokens) + 500 mots body ≈ 670 tokens/article.
  - Note : la fonction `buildEmbeddingInput` cap à 500 mots body, estimation 500 mots × 1.33 token/mot = 665 tokens body + 30 titre/meta = **695 tokens/article**.
- Total 10 000 articles : 10 000 × 695 = **6 950 000 tokens = 6.95M tokens**.
- Coût : 6.95M × $0.13/1M = **$0.904 ≈ 0.85 € pour 10 000 articles**.

**Coût réel pour le corpus actuel estimé :** Si le corpus est ~1 000 articles publiés (estimation conservative pSEO Axion-IA) : ~0.085 € ($0.09). Négligeable.

**Note sur le daily cap** : `OPENAI_EMBEDDINGS_MAX_TOKENS_PER_DAY` default = 1M tokens = ~1440 articles/jour. Backfill 10k articles = 7 jours au cap par défaut. Recommandé : monter cap à 10M temporairement pendant backfill.

## P1 identifiés

### P1-1 : Index manquant pour ORDER BY de keyword-selector

**Requête** : `ORDER BY last_used_at ASC NULLS FIRST, usage_count ASC, term ASC` avec filtre `WHERE vertical = $vertical`.

**Index existant** : `(usage_count, last_used_at)` — ordre inversé, non couvrant pour le filtre `vertical`.

**Index recommandé** :
```sql
CREATE INDEX CONCURRENTLY "keywords_vertical_rotation_idx"
  ON "keywords"("vertical", "last_used_at" ASC NULLS FIRST, "usage_count" ASC);
```
Impact : réduit le sort en mémoire pour la subquery, critique à 747+ keywords avec concurrence 5-10 workers.

### P1-2 : Absence de lock_timeout sur keyword-selector

Sans `lock_timeout`, sous charge pic (concurrence 10 workers × burst), les workers peuvent s'attendre mutuellement. Recommandé :

```typescript
await prisma.$executeRaw`SET LOCAL lock_timeout = '100ms'`;
// puis la requête SKIP LOCKED
```

Ou wrapper dans `$transaction()` avec `timeout: 5000`.

### P1-3 : topic-fingerprint.ts : computeTopicFingerprint retourne null même si VOYAGE_API_KEY présente

`axionia/src/server/content-gen/dedup/topic-fingerprint.ts` lignes 73-78 : Si `hasVoyageKey = true`, la fonction retourne quand même `null` avec un TODO. La couche 3 dedup est donc inopérante même si la clé est présente. Cela doit être documenté explicitement côté opérationnel.

### P1-4 : Daily cap token counter in-memory (reset au boot worker)

`openai-embedder.ts` lignes 34-36 : `const tokenCounter = new Map<string, number>()`. Le compteur est en mémoire et se reset à chaque redémarrage du worker. Avec BullMQ + workers qui redémarrent (Coolify restarts, OOM, deployments), le cap journalier peut être dépassé plusieurs fois par jour. Recommandé : Redis-backed counter (documenté comme "V2" dans les commentaires).

### Script 2 : Vérification version pgvector et paramètres HNSW

```sql
-- Version pgvector installée
SELECT extname, extversion FROM pg_extension WHERE extname = 'vector';

-- Index HNSW actuels et leurs paramètres
SELECT
  schemaname,
  tablename,
  indexname,
  indexdef
FROM pg_indexes
WHERE indexdef ILIKE '%hnsw%'
ORDER BY tablename;

-- Taille des index vector en production
SELECT
  i.relname AS index_name,
  t.relname AS table_name,
  pg_size_pretty(pg_relation_size(i.oid)) AS index_size
FROM pg_class i
JOIN pg_index ix ON i.oid = ix.indexrelid
JOIN pg_class t ON ix.indrelid = t.oid
WHERE i.relname LIKE '%hnsw%' OR i.relname LIKE '%embedding%';
```

### Script 3 : Diagnostic backfill articles manquants

```sql
-- Compter articles publiés sans embedding (besoin de backfill)
SELECT
  COUNT(*) FILTER (WHERE embedding IS NULL) AS "sans_embedding",
  COUNT(*) FILTER (WHERE embedding IS NOT NULL) AS "avec_embedding",
  COUNT(*) AS "total"
FROM articles
WHERE status = 'published';

-- Estimation coût backfill : tokens estimés (4 chars/token)
SELECT
  COUNT(*) AS articles_a_backfiller,
  SUM(
    CEIL(
      (COALESCE(LENGTH(title), 0) + COALESCE(LENGTH(meta_description), 0)
       + LEAST(COALESCE(LENGTH(body), 0), 8000)) / 4.0
    )
  ) AS tokens_estimes,
  ROUND(
    SUM(
      CEIL(
        (COALESCE(LENGTH(title), 0) + COALESCE(LENGTH(meta_description), 0)
         + LEAST(COALESCE(LENGTH(body), 0), 8000)) / 4.0
      )
    ) * 0.13 / 1000000.0, 4
  ) AS cout_usd
FROM articles
WHERE embedding IS NULL AND status = 'published';
```
