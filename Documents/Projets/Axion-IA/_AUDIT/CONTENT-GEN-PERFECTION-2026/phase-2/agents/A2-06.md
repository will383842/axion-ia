## 1. Gestion erreurs Anthropic API (14/20)

### Retry backoff — PRÉSENT

`src/server/content-gen/lib/retry.ts:25-48` — `withRetry()` implémenté :

```typescript
const DEFAULT_DELAYS_MS: ReadonlyArray<number> = [10_000, 30_000, 60_000];

export async function withRetry<T>(fn: () => Promise<T>, opts: RetryOptions = {}): Promise<T> {
  const maxAttempts = opts.maxAttempts ?? 3;
  const delays = opts.delaysMs ?? DEFAULT_DELAYS_MS;
  // ...
  if (err instanceof ProviderError && !err.retryable) {
    throw err; // auth_failed, cost_cap_reached, content_filter → no retry
  }
```

Délais **10s / 30s / 60s** — linéaire (non exponentiel malgré le nom). Pas de jitter. BullMQ queue-level : `backoff: { type: "exponential", delay: 5000 }` (queues.ts:33).

### Codes erreur Anthropic — mapping `mapAnthropicError()` (anthropic.ts:87-121)

| Code HTTP | Géré | retryable | Note |
|-----------|------|-----------|------|
| 401/403 | ✅ | false | auth_failed |
| 429 | ✅ | **true** | rate_limited — déclenche withRetry |
| 500+ | ✅ | true | down |
| APIConnectionTimeoutError | ✅ | true | timeout |
| APIConnectionError | ✅ | true | down |

**GAP critique** : `overloaded_error` Anthropic (HTTP 529 / body `error.type = "overloaded_error"`) NON géré explicitement. La branche `status >= 500` le capte indirectement (retryable=true) mais sans détection précise — le message d'erreur ne distingue pas 529 de 500, ce qui empêche un backoff spécifique plus long (Anthropic recommande 60+ s sur overloaded).

### Timeout configuré

- `anthropic.ts:35` : `DEFAULT_TIMEOUT_MS = 60_000` → injecté via `new Anthropic({ timeout: DEFAULT_TIMEOUT_MS })`
- `openai.ts:30` : `DEFAULT_TIMEOUT_MS = 30_000`
- Le timeout SDK Anthropic coupe le streaming mid-flight mais l'erreur remonte via `APIConnectionTimeoutError` → correctement mappé retryable.

**Pénalité** : -3 pts (overloaded_error non distingué) + -3 pts (pas de jitter anti-thundering-herd sur les 3 workers concurrents × retry simultané).

## 2. Circuit breakers (10/20)

### Library — ABSENTE (implémentation maison in-memory)

`src/server/content-gen/providers/provider-router.ts:28-96` :

```typescript
// Circuit breaker in-memory V0 (Sprint 1 Day 2 step 16:00)

```

Cycle implémenté : `closed → open (5 failures/30s) → half-open (après 60s) → closed/open`.

### GAPs critiques

**1. État in-memory, non partagé entre workers** : `circuits` est un `Map` module-level. Avec `concurrency: 5` sur content-gen-worker, chaque process worker (si plusieurs instances) maintient un circuit **indépendant**. 5 workers peuvent chacun ouvrir leur circuit localement mais pas coordonner. La TODO "Day 5 V2 : passer à Redis-shared" n'est PAS réalisée.

**2. Tests circuit-breaker SKIPPÉS** : `src/server/content-gen/providers/__tests__/circuit-breaker.spec.ts:27-32` — les 2 tests substantiels sont `it.skip(...)`. Seul `_resetCircuits()` est testé. Le comportement réel n'est donc pas validé en CI.

**3. Fallback text role incorrect** : `ROLE_TO_PROVIDERS.text = [openaiProvider, anthropicProvider]` — OpenAI est PRIMARY, Anthropic est FALLBACK. En cas d'outage total Anthropic (primary down), le fallback va vers OpenAI. Mais si OpenAI est aussi down, les 5 retries × 2 providers = 10 tentatives × 60s max = potentiellement **10 minutes de blocage** par job.

**4. Absence de protection runaway** : Si Anthropic est down durablement (>60s), les jobs BullMQ `attempts: 3` + `backoff: exponential` vont générer `3 × 5 workers = 15 tentatives simultanées` toutes les 5s/10s/20s. Pas de `concurrency: 1` dégradé quand circuit ouvert.

**5. Alerte circuit-ouvert** : Un `console.warn` est émis (provider-router.ts:78) mais pas d'alerte Telegram. La TODO `content-gen-alerts.ts:87` référence `R11-provider-circuit-breaker.md` mais l'alerte automatique n'est pas implémentée.

**Pénalité** : -10 pts (in-memory non partagé = circuit breaker inefficace multi-process + tests skippés + pas d'alerte).

## 3. Poison pills BullMQ (16/20)

### Config `attempts` et `backoff`

`src/server/queue/queues.ts:31-36` — options globales :

```typescript
const defaultJobOptions = {
  attempts: 5,
  backoff: { type: "exponential" as const, delay: 5000 },
  removeOnComplete: { age: 7 * 24 * 3600, count: 1000 },
  removeOnFail: { age: 30 * 24 * 3600, count: 5000 },
};
```

Override par queue :
- `content-gen` : `attempts: 3`
- `content-publish` : `attempts: 3` (via `removeOnFail` dans worker)
- `content-quality-improver` : `attempts: 2`

### Après maxAttempts — DLQ behavior

BullMQ place automatiquement le job en état `failed` après épuisement des tentatives. `removeOnFail: { count: 5000 }` conserve les 5000 derniers jobs failed en Redis (pas de purge immédiate). **Pas de DLQ dédiée** — les jobs échoués restent dans la queue principale en état `failed` (accessible via BullMQ UI ou API).

### UnrecoverableError — PRÉSENT

`content-gen-worker.ts:173` :
```typescript
throw new UnrecoverableError(`ContentGenJob ${contentGenJobId} not found`);
```
Usage correct : job introuvable en DB → `UnrecoverableError` évite les retries inutiles.

### stalledInterval / lockDuration — ABSENTS

Aucun `stalledInterval`, `lockDuration`, ni `lockRenewTime` configuré dans les 3 workers audités. BullMQ utilise ses **defaults** : `lockDuration: 30_000ms` (30s), `stalledInterval: 30_000ms`. Or les jobs content-gen peuvent durer **60-90s** (retry withRetry: 10+30+60s = 100s max si 3 tentatives). Un job qui dépasse 30s de lock peut être considéré **stalled** et re-enqueué — causant une **exécution double** (two LLM calls, deux inserts Article potentiels).

### Scénario poison pill

Job avec `inputPayload.title = ""` (chaîne vide) :
1. `checkDedup` est skippé (title falsy) → pas de protection
2. `generator.generate()` appelé avec title vide → génère un article potentiellement invalide
3. `plagiarism.passed` peut être true (bodyText court) → passe toutes les gates
4. Article inséré en DB → ReviewQueue pending

Job avec `contentGenJobId` valide mais `outputJsonRaw = null` envoyé au publish-worker :
- `content-publish-worker.ts:169` : `throw new Error("ContentGenJob ${cgJob.id} has no outputJsonRaw")` → retries × 3 → failed. **Correct.**

**Pénalité** : -4 pts (lockDuration non configuré = risque double-exécution sur jobs longs).

## 4. Rollback publication (12/20)

### Transaction atomique publish — PRÉSENTE mais PARTIELLE

`content-publish-worker.ts:239-301` — `prisma.$transaction()` couvre :
- `Article.create`
- `ArticleTranslation.create`
- `ContentGenJob.update` (status → published)

**Ce qui est hors transaction** (après le `await article`):
- `logProvenance()` — fire-and-forget
- `enrichOutputWithNewsArticleJsonLd()` — log seulement
- `enqueueIndexingForTier1()` — IndexNow enqueue (BullMQ add)
- `getFactCheckQueue().add()` — enqueue fact-check
- `getQaExtractQueue().add()` — enqueue Q/R extraction
- `revalidateContent()` — ISR revalidate

### Scénario IndexNow fail après DB write

```
prisma.$transaction() → SUCCESS (Article créé, status=published)
↓
enqueueIndexingForTier1() → FAIL (Redis down, ECONNREFUSED)
↓
throw Error → job BullMQ retry
↓
2ème tentative : prisma.$transaction() → FAIL (slug duplicate P2002 sur ArticleTranslation)
↓
UnrecoverableError ? NON → throw Error standard → retries × 3 → all fail → job.failed
```

**Impact réel** : L'Article est en DB avec `status=published` mais IndexNow n'a jamais été pingué. Il reste publié (le code de retry ne rollback pas la transaction précédente). L'article est **orphelin** : publié en DB, visible via accès direct URL, mais absent des sitemaps (ISR pas revalidé) et Google non notifié.

**Aucun rollback automatique** du Article.create si les étapes post-transaction échouent.

### MAX_PUBLISH_PER_DAY mid-batch

`content-publish-worker.ts:141-155` :
```typescript
if (publishedToday >= MAX_PUBLISH_PER_DAY) {
  const nextWindowTs = msUntilDripStart();
  await job.moveToDelayed(nextWindowTs, job.token);
  return;
}
```

Comportement : `moveToDelayed()` plutôt que fail → le job est **reporté** au lendemain 8h CET. Correct pour la limite quotidienne. Pas de rollback nécessaire ici (aucun Article créé avant ce check).

### Rollback manuel — PRÉSENT mais non atomique

`src/server/actions/content-gen/article.ts:408-443` — `rollbackArticle()` :
```typescript
await prisma.article.update({
  where: { id: articleId },
  data: { status: "draft", indexationTier: "tier_3_noindex_nofollow", promotedAt: null },

```

Simple `update` (pas de transaction). Si `pingIndexing()` échoue après l'update, l'article est en draft en DB mais Google n'a pas reçu le signal `URL_DELETED`. **Pas d'idempotence** sur le rollback.

### ReviewQueue update non transactionnel

`src/server/actions/content-gen/review.ts:313` — `prisma.$transaction([...])` (batch parallèle) couvre l'approbation review. Correct.

**Pénalité** : -8 pts (IndexNow fail → orphan article non rollbacké + rollback manuel non atomique + pas d'idempotence sur re-run).

### Fix P0-2 — Wrapper post-transaction avec cleanup sur échec

```typescript
// content-publish-worker.ts — après prisma.$transaction()
const article = await prisma.$transaction(async (tx) => { /* ... */ });

try {
  if (promoteToTier1) {
    await enqueueIndexingForTier1({ articleId: article.id, slug: slugCandidate, isNews });
  }
  await revalidateContent({ paths });
  // fact-check, qa-extract (déjà try/catch individuels)
} catch (postTxErr) {
  // Rollback : repasser en draft si les étapes critiques échouent
  await prisma.article.update({
    where: { id: article.id },
    data: { status: "draft", indexationTier: "tier_3_noindex_nofollow" },

  await logStepError(cgJob.id, "post_tx_rollback",

  throw postTxErr; // BullMQ retry
}
```

### Fix P0-3 — Circuit breaker Redis-shared (migration V0 → V1)

```typescript
// provider-router.ts — migration vers Redis-shared state
import { redis } from "@/lib/redis";

async function isCircuitOpen(key: ProviderKey): Promise<boolean> {
  const openedAt = await redis.get(`circuit:${key}:openedAt`);
  if (!openedAt) return false;
  const elapsed = Date.now() - parseInt(openedAt, 10);
  if (elapsed > OPEN_DURATION_MS) {
    await redis.del(`circuit:${key}:openedAt`);
    await redis.set(`circuit:${key}:halfOpen`, "1", "EX", 30);
    return false;
  }
  return true;
}
```
