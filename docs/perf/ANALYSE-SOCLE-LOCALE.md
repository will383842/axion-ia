# Analyse du socle `[locale]` : d'où viennent les ~294 KB gz de First Load JS

> Analyse seule. Aucun code de production modifié. Mesuré le 2026-11-26 sur `origin/main` (`1abd8256d`).
> Suite de `.pr/perf-journee-ia-first-load.md` (branche `perf/journee-ia-first-load`).

## 1. Méthode et limites

- Build : `next build --webpack --experimental-build-mode compile` avec les stubs `stub.invalid`, `SKIP_NEXT_TYPECHECK=true`.
  - `ANALYZE=true` (`@next/bundle-analyzer` est configuré) **fait planter le build** (SIGABRT, OOM à 8 Go sur un runner de 15 Go). Le build sans `ANALYZE` passe avec `--max-old-space-size=12288` (8 Go ne suffit pas à coup sûr).
  - Pas de source maps navigateur. Les modules ont été **découpés à la main** dans chaque chunk (script jetable, hors dépôt) et identifiés par leurs chaînes caractéristiques (`MISSING_MESSAGE`, `dismissable`, `Invalid input`, `_sentryRouteManifest`…). Les poids par module sont des gzip de tranches de texte : ordre de grandeur, pas une mesure exacte.
- Poids d'une route = fichiers de `page_client-reference-manifest.js` + `rootMainFiles` + `polyfillFiles`, gzip un à un (même méthode que l'analyse précédente). Borne haute : c'est ce que Lighthouse chargera au plus.
- Mesure de `[locale]/a-propos` : **306,4 KB gz sur 28 fichiers** (294 KB mesurés l'analyse précédente ; la tête de `main` a grossi depuis).

### Correction importante : les polyfills ne comptent pas

`polyfills-*.js` (38,7 KB gz) est injecté par Next avec `noModule: true` (`node_modules/next/dist/server/app-render/app-render.js:1899` et `:4915`). Un navigateur qui supporte les modules ES **ne le télécharge pas**. Le First Load réel d'un visiteur Chrome ≥ 109 / Safari ≥ 16.4 est donc **≈ 267,7 KB gz**, pas 306. (Le HTML n'est pas généré en mode `compile`, je n'ai donc pas relu la balise dans une page rendue : à confirmer par un `curl` sur la prod.)

### Ce que cette ventilation dit

1. **Environ 125 KB gz sont incompressibles** : React (62) + runtime routeur de Next (~60) + bootstrap (~1). Même un layout vide ne passerait pas sous ~125-140 KB. Cohérent avec la dette « shell partagé 135,75 KB brotli » d'`AGENTS.md`.
2. **La cible de 75 KB gz par route n'est donc pas atteignable avec Next 16.3 App Router**, quoi qu'on fasse dans le layout. Le plancher mesurable est ≈ 140 KB gz. Décision à prendre par Will (ADR) : requalifier la cible (ex. « socle applicatif ≤ X KB hors framework ») plutôt que de la poursuivre.
3. **Environ 70-85 KB gz sont du code applicatif ou de bibliothèques évitables** (zod, route manifest ×2, Radix Dialog, tailwind-merge, use-intl, next-intl navigation, web-vitals/attribution, lucide).
4. Sentry client lui-même est **déjà chargé à la demande** (`src/lib/observability/sentry-client-lazy.ts`) : ses chunks (`43678`, `90034`, 127 et 155 KB gz) ne sont pas dans le First Load. Seul son **manifeste de routes** fuit dans le socle.

## 3. Polyfills et cible navigateurs

- `package.json` : `browserslist` = Chrome/Edge ≥ 109, Firefox ≥ 115, Safari/iOS ≥ 16.4, ChromeAndroid ≥ 109 (déjà « modern-only », cf. `_browserslist_doctrine`). Pas de `.browserslistrc`.
- **Une cible plus moderne ne retire rien** : le bundle `polyfills-*` de Next (core-js, 110 KB brut) est fixe, indépendant de browserslist, et déjà exclu du téléchargement moderne par `noModule`. Gain réel : 0 KB. Le gain apparent (38,7 KB) disparaît simplement du calcul si l'on mesure comme le navigateur (§1).
- Ce que browserslist influence (transpilation SWC du code applicatif) est déjà à son plus bas.
- Ne pas gaspiller de temps ici : le levier est ailleurs.

### Gain cumulé réaliste

- Lots 1 + 2 (+ 5) : **≈ 28 KB gz**, faible risque, quelques heures. Priorité.
- Lots 3 + 4 : **≈ 10 à 18 KB gz** supplémentaires, risque moyen (a11y du menu mobile).
- Lot 7 : ≈ 21 KB gz, refonte lourde ; seulement si le budget le justifie.
- Total atteignable raisonnablement : **267,7 → ≈ 230 KB gz** de First Load réel. **Le budget de 75 KB par route reste hors d'atteinte** (plancher ≈ 140 KB gz, cf. §2).

### Ordre proposé

1. `routeManifestInjection: false` (une ligne, 13,7 KB) — à vérifier d'abord : que Sentry prod n'exploite pas le regroupement par route côté navigateur.
2. Analytics sans `@/env` (12,9 KB).
3. `Sheet` dynamique (9,5 KB) avec préchargement au `pointerenter`.
4. `cn` allégé dans le nav, `web-vitals` dynamique.
5. Décision de Will sur la cible de 75 KB (ADR) avant tout chantier sur le provider next-intl.

Chaque lot doit être mesuré avant/après avec le même script de somme de chunks (les **octets** se lisent sur une passe, cf. `AGENTS.md`) ; l'effet sur LCP/INP/TBT ne se lit qu'en médiane sur plusieurs runs Lighthouse, jamais sur une paire de mesures.

## 5. Non vérifié

- Le HTML rendu (balise `noModule`, `<link rel=preload>` réellement émis) : le mode `compile` ne pré-rend pas.
- Les gains sont des estimations (gzip de tranches) ; les chunks se redécoupent après chaque changement, donc les chiffres bougent.
- `ANALYZE=true` n'a pas abouti (OOM) : pas de treemap, donc pas de poids exact par paquet.
- Aucun test, typecheck ni lint lancé : aucun code modifié.
